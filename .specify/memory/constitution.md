# tu-assistant Constitution

## Core Principles

### I. 条款准确与出处可溯（NON-NEGOTIABLE）

- 任何交付给用户的输出（咨询回答、普法文章）中，凡出现具体法律条款，MUST 标明出处：
  文件全称、版本、条款编号（精确到条，有款、项时精确到款、项）。
- 输出中的条款编号与原文 MUST 能与知识库逐字比对；比对不通过的内容 MUST NOT 交付给用户。
- 知识库（项目方提供并经入库校验的文件）是条款内容的唯一权威来源。无论采用何种技术方案，
  模型生成的条款内容都必须以知识库为准接受校验。

**理由**：本项目服务于工会法律工作，条款引用错误会直接误导用户的工作判断，
且错误难以被用户自行发现。

### II. 不编造，可拒答（NON-NEGOTIABLE）

- 对知识库范围外的问题，系统 MUST 明确告知无法回答，MUST NOT 编造条款、案情结论或法律依据。
- 当关键事实不足时，系统 MUST 追问或明确标注结论所依赖的未确认事实，MUST NOT 自行补全事实。
- 系统输出 MUST 附带"仅供参考，不构成法律意见"一类的提示。

**理由**：对法律类系统而言，一个自信的错误答案比"不知道"危害更大。

### III. 用户数据不出域（NON-NEGOTIABLE）

- 用户在对话中输入的内容视为非公开数据。未经项目方书面同意，MUST NOT 发送至项目方环境以外的
  任何服务，MUST NOT 用于评测或模型训练。
- 生成的普法文章 MUST 使用虚构的人物与单位名称，MUST NOT 出现用户在对话中提供的真实身份信息。
- 只有项目方提供的公开法律文档与公开案例，才允许交给外部服务处理（如数据合成、评测打分）。

**理由**：工会工作人员咨询时常会描述真实的职工与单位情况，这些信息不属于公开数据。

### IV. 自有模型，私有部署

- 线上运行时，意图理解、条款判断与内容生成能力 MUST 由项目方自有的模型提供，
  且 MUST 能在项目方自己的环境中私有化部署。
- 外部大模型服务 MAY 用于离线开发环节（数据合成、评测打分、对照基线），但 MUST NOT 出现在
  线上运行链路中。
- 模型权重、训练数据与训练配置 MUST 由项目方掌握并可复现训练。

**理由**：拥有自有模型是项目方明确的业务约束。

### V. 评测驱动决策

- 技术选型、模型或训练方式变更、数据变更、提示词变更，MUST 以标准评测集上的量化结果为依据；
  没有评测数据支撑的结论 MUST NOT 作为决策依据。
- 评测集 MUST 先于对应的实现建立，并与训练数据隔离：评测用例的问法 MUST 与训练数据不同。
- 任何影响模型行为的变更合入主线前，MUST 附带回归评测报告，证明核心指标（条款识别、
  出处准确、拒答）没有低于规格规定的阈值。
- 不同方案之间的对比 MUST 使用同一评测集和同一指标口径。

**理由**：法律领域的效果无法靠主观感觉判断；当前处于技术选型阶段，结论必须经得起复查。

### VI. 简单优先，可复现

- 在满足规格要求的前提下，MUST 优先采用最简单的方案；引入额外复杂度（新组件、新训练阶段、
  更大模型）MUST 在 plan 中说明理由，并有评测数据证明其必要性。
- 每次实验与训练 MUST 记录可复现所需的全部信息：数据版本、知识库版本、模型与基座版本、
  训练配置、随机种子、评测集版本。
- 数据处理与评测流程 MUST 能用同一套脚本从小规模（几十篇）扩展到正式规模（约 1000 篇），
  不得为小规模实验单独写一次性流程。

**理由**：项目将从 30–50 篇文档扩展到约 1000 篇文档，且需要反复迭代；
不可复现的实验结果无法用于决策。

## 数据与合规约束

- 知识库只收录项目方提供的文件；收录范围由项目方决定，开发过程中不得自行增删或预设文件类型。
  为规模扩展评测引入的同类公开文档 MUST 与正式知识库分开管理并明确标注。
- 每份文件 MUST 记录版本与效力状态；默认依据现行有效版本作答。
- 评测集只能来自公开资料（公开文档、公开案例）以及人工编写或合成后经人工校验的用例；
  MUST NOT 包含真实用户的对话内容。
- 交互语言为中文。地方性法规、维权文书等本期范围外的内容，MUST 先通过新的规格（`/speckit-specify`）
  纳入，不得在实现中顺带加入。

## 开发流程与质量门禁

- 采用 Spec-Driven Development：规格（spec）→ 计划（plan）→ 任务（tasks）→ 实现（implement）。
  需求变更 MUST 先更新规格，再修改实现。
- 每份 plan MUST 通过 Constitution Check，逐条说明是否符合本文件的原则；有偏离时 MUST 在
  plan 的复杂度说明中给出理由并经项目方确认。
- 确定性的逻辑（文档解析与条款拆分、出处比对校验、评测打分）MUST 有自动化测试。
- 涉及模型行为的变更 MUST 运行回归评测，评测报告随变更一起保存。
- 规格、计划及其他文档的提交 MUST 经项目方审阅同意后进行。

## Governance

- 本文件优先于其他开发惯例与约定；与本文件冲突的做法须修改，或先修订本文件。
- 修订流程：提出书面修订说明（修改内容、理由、影响范围）→ 项目方确认 → 更新本文件及版本号 →
  检查并同步受影响的规格、计划与模板。
- 版本规则（语义化版本）：
  - MAJOR：删除原则，或对原则做出不向后兼容的重新定义；
  - MINOR：新增原则或章节，或对既有原则做实质性扩充；
  - PATCH：措辞澄清、错别字修正等不改变含义的调整。
- 合规检查：每次 `/speckit-plan` 与 `/speckit-analyze` 时，以及每次评审变更时，都要核对是否符合本文件。
  标注 NON-NEGOTIABLE 的原则不允许以"复杂度说明"的方式豁免。
