## 2. 现象

> **作废（E002）**：本节"现象"来自 `run-20261115-025552`，实测为 1.5B **基座**输出，
> 不代表 `exp-20261114-120250` adapter 的行为。修复后重新评测见 E002 §4
> （1.5B adapter 实际含〔50–60/60）。

### 2.1 指标

| 指标 | 值 |
|---|---|
| 条款召回率 | 0.000 |
| 条款精确率 | 0.000 |
| 引用准确率（校验前） | 0.000 |
| 引用准确率（校验后） | 0.001 |
| 引用判定 | ok=0 / corrected=1 / not_found=5 / incomplete=692 |
| 含〔〕引用标记的回答 | 60 题中 5 题 |

incomplete 占绝大多数：模型大量写"根据《X法》第N条……"这类**裸引用**
（没有〔〕标记、无法唯一定位），校验层只能保留并记为 incomplete；
有几题因复读同一句话，一题就贡献上百个 incomplete。

### 2.2 典型输出（均截断）

**(a) 有结构骨架，但没有引用块；追问被塞进"违法行为认定"**（cand-001，问竞业限制最长多久）：

```text
违法行为认定：
1. 你的亲戚是否与原单位签订了竞业限制协议？
2. 竞业限制协议中关于竞业限制的期限是如何规定的？
……（共 5 个追问）
适用分析：
……竞业限制协议的期限可以由双方协商确定，但最长不得超过三年。
……（以下略）
```

- 标题"违法行为认定 / 适用分析 / 法律责任"学到了，但写成纯文本列表，没有〔〕引用块；
- 5 个追问问题出现在"违法行为认定"下——**追问模式与咨询模式混杂**；
- **事实错误**：竞业限制法定最长两年，模型说"最长不得超过三年"。

**(b) 引用幻觉**（cand-007，工伤相关）：模型输出

```text
〔《工伤保险条例》（2010年修订）第16条第2款〕
> 根据《工伤保险条例》第16条第2款的规定，职工在工作时间……（以下略）
```

- KB 中**没有**《工伤保险条例》，文件、条款号均为编造，校验层判 not_found 并删除；
- 引用块里的"原文"以"根据……的规定"开头，其实是模型自己的分析句，不是条款原文。

**(c) 格式对、条款错**（cand-033，问粉尘防护）：引用了 KB 中真实存在的条款，
校验层用 KB 原文替换（唯一一次 corrected），但该条款内容是劳动合同告知义务，
与粉尘防护无关——校验层能修原文，**修不了定位错误**。

**(d) 复读**（cand-060 等）：后半段"建议：……"同一段落反复出现，直到长度上限。

## 3. 诊断

### 诊断 1：训练/推理分布不一致（事实已核实，因果为推断）

已核实的事实：

- `train.jsonl` 中 **13,801 / 14,493（约 95%）** 样本**没有 system 消息**，只有 user/assistant；
- 有 system 的 **692** 条**全部是意图确认类**（过采样后的 intent），其 system 就是运行时的
  `SYSTEM_TEMPLATE`（`src/tu_assistant/chat/prompts.py`，由 `synth/dialogs.py` 写入）；
- 运行时 `src/tu_assistant/chat/orchestrator.py` 每次请求都拼上这段约 400 字的 system prompt，
  评测也走这条路径。

推断（**尚未验证**）：

- 模型从未在"带 system prompt"的条件下学过知识/咨询类回答（带引用块的那部分）；
- 更糟的是，它可能学到了"看到这段 system prompt → 进入追问模式"的关联。
  这能解释现象 (a) 的追问与咨询混杂，以及引用块几乎全部缺失。

### 诊断 2：1.5B 容量不足（推断）

即便格式修好，1.5B 在"口语场景 → 文件名+条款号"（条款定位）和原文记忆上也可能不行。
编造 KB 中不存在的《工伤保险条例》、事实错误（"三年"），更像容量/知识问题，
而不是格式问题。详见学习文档 L5.6 的"三层能力"。

### 诊断 3：可能欠训（推断）

lr 1e-5 对 LoRA 偏保守（常用 1e-4 量级），最终 val loss 0.79 并未充分收敛，
train 与 val 差距小、曲线仍在缓慢下降，形态上更像欠拟合。
但要注意：**val loss 与评测指标是脱节的**（见 L5.4），val loss 再降也不保证评测变好。

### 综合判断

> **作废（E002）**：以下判断基于基座模型的输出，其证据价值作废。
> 但诊断 1 指出的"95% 样本无 system prompt"数据缺陷本身属实且已修复（尝试 2）。

两个主要原因可能叠加：**分布不一致让格式崩，容量小让内容不可靠**。
先用最便宜的对照实验把两者分开（尝试 1），再决定下一步。

### 其他观察（暂不作为主因）

- 配置中的 `alpha: 16` 在 mlx_lm 中不生效，实际缩放为 `scale: 10`；
- `mask_prompt=false`：loss 也计算 user/system 部分，让 loss 更难反映回答质量；
- 每次 val 只抽 25 条，val loss 曲线噪声大，不宜看单点。

- **对后续的影响**：按既定计划，尝试 2（给全部训练样本补运行时 system prompt）
  仍值得做——分布一致性本身是数据缺陷且成本极低；但不要期待单靠它能救回引用，
  训练侧（尝试 3）需要同时加强：lr 提到 5e-5 量级、3 epoch，
  或直接上 (b) 7B。

#### NaN 根因诊断（2026-11-16）

状态：**已定位**（只诊断，未改 src/、未重训）。临时脚本在 `/tmp/nan_diag/`，未入库；
未读取/输出任何样本内容，只统计长度、索引与数值。

**环境事实**：mlx 0.32.4 / mlx_lm 0.32.2；`mlx-community/Qwen2.5-7B-Instruct-4bit`
虽然 config 写 `torch_dtype: bfloat16`，但 mlx 转换后 scales/embedding 是 **float16**，
训练时的激活（含注意力的 q/k/v）都是 **fp16**。mlx_lm 训练循环**没有梯度裁剪、
没有 NaN 跳步**（`lora.py`/`tuner/` 内无 clip/isfinite；Adam 一旦吃到一次 NaN 梯度，
参数永久变 NaN——这就是"之后全程 nan"的原因）。

**batch 顺序还原（H3 的基础）**：`CacheDataset.itemlen` 返回的是原始 dict 的 key 数
（全部样本都只有 `messages` 一个 key），所以"按长度排序"实际不改变顺序；
`lora.run()` 里 `np.random.seed(42)` 后第一次 `np.random.permutation(8921)` 就是训练顺序。
验证：按此顺序累计的"计 loss token 数"在 iter 50/100/…/700 处与日志 tokens 列
**逐点一致**（8.7k、18.3k、…、85.4k@500、93.3k@550、100.0k@600），顺序还原可信。

| 假设 | 判定 | 证据 |
|---|---|---|
| **H2** mask_prompt 下 0 目标 token → 0/0 | **排除** | `default_loss` 确实是 `sum/ntoks`，ntoks=0 会得 NaN（且梯度 inf×0=NaN），但用 Qwen tokenizer + chat template 实测 train 8,921 条：最长 **2,015 token**（无一超过 2,048，无截断），assistant 段最少 **7 token**，每条计 loss token 最少 8，**ntoks≤0 的 0 条、<5 的 0 条**（<20 的 406 条）；日志 tokens 列在 NaN 之后仍按预期增长，也说明 ntoks 从未为 0 |
| **H3** 特定样本触发 | **部分支持（样本只是"扳机"）** | iter 501–550 实际样本索引已还原（如 501→811、505→1446、507→8617），长度 193–1,057、ntoks 15–768，无异常。用 **0000500 检查点**逐条前向+反向（iter 495–560 共 66 条）：**前向 loss 全部有限**（0.43–2.35），但 **29/66 条梯度出现 NaN**，第一条是 iter 505（样本 1446），与日志"iter 501–550 窗口内出现 NaN"吻合；同样 66 条在**基座**上梯度全部有限。NaN 不取决于样本内容，而是取决于"这个检查点状态 + 样本恰好让最后一层注意力 logit 超阈" |
| **H5** fp16 注意力反向溢出（新发现） | **支持（直接原因）** | ①NaN 梯度的分布：第 27 层（最后一层）`o_proj`、`mlp` 的梯度有限，`q/k/v_proj` 及以下 0–26 层全部 NaN（19,553,280 / 20,185,088 个）→ NaN 产生于**第 27 层 SDPA 的反向**。②最小复现：取出第 27 层的 q/k/v，单独对 `mx.fast.scaled_dot_product_attention(mask="causal")` 求 vjp：**fp16 → NaN（4.5 万–7.7 万个），同一份数据转 bf16 / fp32 → 0 个 NaN**。③目标行的最大缩放后注意力 logit：基座 2,031–2,438，0000500 检查点 **5,196–6,149**；5,196 那条不 NaN、≥5,971 的全 NaN（阈值约 5.2k–6k，经验值）。④把注意力换成手写 fp32 实现后，同样 6 条 NaN 样本梯度全部有限（范数 6–10），loss 与原实现一致到 1e-4。⑤从 0000500 出发、fp32 注意力、lr 5e-5（新 Adam）按真实顺序跑 iter 501–539：**39 步全部有限**，loss 均值 0.94，越过了原来的 NaN 点（505/507/511/…）。⑥probe 未开 grad checkpoint、未 `mx.compile` 也能复现 → 与 grad_checkpoint/compile 无关 |
| **H1** lr 过高导致发散 | **部分支持（加速因素，不是根因）** | 没有出现"loss 爆炸→参数爆炸"式的发散：0000500 权重最大 \|A\|=0.036、\|B\|=0.0205，与 1.5B 训完 29k 步的 0.063/0.021 同量级；在 fp32 注意力下 lr 5e-5 能稳定继续训练（见 H5 ⑤）。但 lr 决定 logit 增长速度：无 warmup 时 iter 60–100 就 NaN，warmup 500 时恰在 lr 到峰值后 NaN，1.5B（lr 1e-5）29k 步没出事（1.5B 未实测 logit，推断）。另：从 0000500 用低 lr 续训**无意义**——该状态下 fp16 反向已经对 44% 样本 NaN，第一步之前就会坏，与 lr 无关 |
| **H4** 4bit / 权重数值异常 | **排除（权重层面）；精度层面并入 H5** | 0000500 检查点 392 个张量全部有限；ΔW=scale·A·B 的 Frobenius 范数中位数 1.60，最大 6.72（layer 26 up_proj），**layer 27 q_proj 为 4.39（约 2.7× 中位数）**，正是它把最后一层的 q 推向基座里本就很大的 k 方向（基座第 27 层 \|k\| 最大 420）→ logit 从 ~2.4k 涨到 ~6.1k。问题不在 4bit 量化本身，而在激活用 fp16 |
| iter 500 loss 尖峰 1.366 | **无法判定** | 尖峰窗口（iter 451–500）参数仍是有限的、每一步梯度也都有限（否则 0000500 会是 NaN）；可能是 logit 上涨的前兆，也可能就是那 50 条样本难（基座在其中多条上 loss 2.7–3.7）。无 iter 450 检查点，无法区分 |

**附带发现（不是 NaN 原因）**：mlx_lm 0.32.2 的 mask 是 `steps <= length`，
batch 1 时会把序列末尾后的**1 个 padding 位（token id 0）也算作目标**，每条样本多学一个
"`<|im_end|>\n` 之后接 id 0"的 token。对生成基本无影响（生成在 `<|im_end|>` 停止），记录备查。

**最终结论**（置信度：直接原因 **高**；旧数据集 iter 60–100 NaN 属同一机制 **中**，因无检查点无法直接复现）：

> 训练中 LoRA（scale 10、lr 爬到 5e-5 峰值）把**最后一层注意力的 logit**从 ~2.4k 推到 ~6k，
> 越过了 **fp16 下 mlx `fast.scaled_dot_product_attention` 反向**的溢出阈值；前向仍然有限，
> 但某一步（iter 501–550 之间，按还原顺序是 iter 505）反向产生 NaN 梯度，mlx_lm 没有
> NaN 跳步也没有裁剪，Adam 把 NaN 写进全部参数，此后全程 nan。
> 不是零目标 token（H2 排除），不是毒性样本，也不是"权重发散爆炸"。

**0000500 检查点健康度**：权重全部有限，量级正常；前向 loss 在 66 条训练样本上均有限；
valid 前 100 条（seed 0）val loss **1.214**，基座 2.128。可以拿去评测
（推理只走前向，不受反向溢出影响）。注意 1.214 高于日志 iter 400 的 0.888——
两者抽样不同（日志只抽 25 条），且没有 iter 400 检查点可比，是否已有轻微退化无法判定。

## 5. 教训

- **loss 持续下降 ≠ 任务指标好**。本次 train/val loss 一路下降、没有过拟合迹象，
  评测召回却是 0。要尽早用小规模真实评测"冒烟"，而不是等约 4 小时训完才发现。
- **训练数据要覆盖运行时的真实输入形态**（包括 system prompt）。
  这类问题在数据集清单里加一个"system 覆盖率"统计就能提前发现。
- **长任务必须和 agent 的 shell 脱钩**：用 `nohup` / 独立会话启动，配合 `caffeinate`，
  并且接电源。尝试 3 的 7B 训练挂在后台 subagent 的 shell 下，很可能随 subagent 结束被一起杀掉。
- **训练要定期存 adapter 检查点**（mlx_lm 的 `save_every`）。我们的封装把它默认设成了
  总 iter 数，等于只在最后存一次，中断就全损。**已修复**：`mlx_train.py` 缺省改为
  500，`demo-7b.yaml` 显式 `save_every: 500` 并记入 manifest。
- **动手前先估总耗时**：要算的是"s/iter × iter 数"，不能只看 tok/s。`mask_prompt`
  下日志里的 tok/s 只统计计 loss 的 token，而长 system prompt 不计 loss，却照样花计算。
- **"前向有限"排除不了 NaN**：NaN 可以只出现在反向（本次是 fp16 注意力反向溢出）。
  排查 NaN 要对检查点做"前向 + 反向"并按层看梯度从哪里开始非有限；
  训练循环要有 NaN 守卫/早停，否则一次坏梯度就毁掉后面全部训练。
- **续训压低的是 loss，不一定是行为**：同分布续训 8,421 步把 train loss 从
  ~0.9 压到 ~0.5，greedy 输出却 42/60 逐字不变——回答模式在训练早期
  （全局 ~500 步）就已锁定，后续步数主要增强置信度。判断"是不是训练量不够"
  之前，先对两个检查点的输出做逐字 diff；逐字相同就不用再加 epoch。
- **先看训练特有标记出现没有，再细看指标**：抽查第一眼就查训练数据特有的
  表面标记（本次是〔〕与 `（YYYY-MM-DD）` 版本标签）在输出中出现与否——
  0/60 时其余指标都不用细看。模型会学成"宏观骨架 + 基座表面习惯"的混合体：
  引《法名》第N条的骨架像训练数据，括号标签与措辞却全是基座风格；
  引用分布也是基座通识（全国大法），KB 特有文档一次都没被引到。
