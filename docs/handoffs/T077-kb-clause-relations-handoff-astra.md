## 2. 准备两份供决策的材料

1. **关系修订表。** 每行列出文件与版本、责任条款 ID、能定位条款的简短原文片段、旧关系、新建议、理由和待确认项。原文写明款或项时应能定位到对应行。遇到整条、并列条号、目标缺失或歧义，逐项说明处理依据。当前规则只捕获条号，再取款号最小的代表行，这解释了六处错款为何会重复出现。[关系提取](../../src/tu_assistant/kb/relations.py)
2. **条与第一款的口径对照表。** 用同一条至少有两款的例子演示四种输入：明确引用第一款并附其原文、引用整条并附全文、历史样本只写条号但引文唯一匹配第一款、只写条号且无引文。分别给出建议的关系端点、展示标记、原文范围、校验结果和 SC-005 匹配方式。另用单款条文和含项的款做对照。当前校验器可按引文唯一定位某一款，歧义时返回不完整；历史兼容行为须列明。[引用校验](../../src/tu_assistant/citation/verify.py) · [引用契约](../../specs/001-legal-clause-assistant/contracts/citation-format.md)

建议新生成的多款条文第一款显式写款号。对整条引用，要结合责任原文的适用条件审阅覆盖范围。若拟新增条级端点或展开为多个款级端点，先用一个例子展示存储、查找、训练引文及 SC-005 分母会如何变化，特别说明同一责任条款会否重复计分。

## 4. 修正规则，在新 KB 上验证确认流程

1. 按审定口径修正提取和引用处理，通过项目正常入口重跑候选。用自编测试材料覆盖明确第 2/4 款、同句多处引用、整条、无效编号，以及旧样本只给条号的情形。核对被引用条款与责任条款的方向。
2. 从固定旧 KB 派生新版本，写入新的版本清单，保留旧版本供历史 run 复现。显式指定版本和产物目录。现有确认入口只插入标为真的行，换端点后旧边可能继续存在。应用审定差异时须同时处理旧边撤销、新边确认，并保留无关已确认关系。[确认入口](../../src/tu_assistant/cli.py) · [关系存储](../../src/tu_assistant/kb/store.py)
3. 验证正常导入、重复导入同一批次，以及中途遇到坏行或不存在的端点。验收时逐项对账：新库只包含审定变更，旧错边已撤销，拒绝和待查项未作为已确认关系生效，失败不会留下半批数据；旧库校验值与第 1 步相同。

## 5. 用相同输入核对下游影响

| 对象 | 核验方法与交付证据 |
|---|---|
| 知识训练样本 | 对两版 KB 分别运行现有关系样本生成器，按依据 ID、责任 ID 和实际引用文本列出增删改。沿训练实验 manifest 定位实际 train/valid 文件，查受影响样本是否落盘、在哪个 split、重复几次。若历史序列化结果缺少 ID，注明文本匹配方法及无法归因的记录。[样本生成器](../../src/tu_assistant/synth/knowledge.py) |
| SC-005 | 固定同一份模型输出，在两版 KB 上重算。先固定引用 ID 只换关系表，再用同一原文走两版完整引用校验，以区分关系变化和解析变化。逐题列出应补关系数、命中数、得分或无适用关系；若历史 run 未命中问题关系，用固定诊断例另证差异，单列历史结果。[指标实现](../../src/tu_assistant/eval/metrics.py) |

| T052/T053/T057 | 重跑文章素材筛选，报告可用配对数、被跳过的原因。对多违法组合另外检查能否发生于同一纠纷。用新口径复核已通过 T052 的三条候选，记录受影响的引用与后续处理，历史验收稿单独保留。 |
