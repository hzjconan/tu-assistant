## 2. 实施顺序

1. **锁定输入、复算重合并校准历史基线。** 在 `artifacts/logs/t075/<尝试号>/` 登记 Git 版本、依赖锁文件、MLX/mlx-lm 版本、基座快照、两版数据清单、父权重和 C 权重、两版 SQLite、评测文件、prompt 和历史两份 run 的路径与哈希。新 train/valid SHA-256 前 12 位为 `d15ca5efd4b1` / `e1fb6779782c`，旧 `artifacts/datasets/ds-kb-20261113-093057-8410/train.jsonl` 为 `e73c285ece72`，旧/新 KB 为 `e6a964968c69` / `40d4ea703334`。检查行数、两套已有权重全有限、快照可本地加载；重跑第 3 节历史 compare，保存输出与退出码。

   在实验记录中复算并登记下列数值：逐行读取新旧数据集各自的 `train.jsonl`，键为完整有序的 `messages`（含 system、各轮 role/content，按 `json.dumps(messages, sort_keys=True, ensure_ascii=False)` 序列化）。将旧 train 键建成集合，逐行检查新 train 是否命中。每次命中后保留旧集合中的键，因此过采样重复行按训练文件中的出现次数累计。设计时实测 **8,648/8,962 行（96.5%）命中，314 行未命中**。314 行去重后只有 **104 个不同对话键**；该口径衡量训练行复用，不能据此推断独立案情数量、父模型实际看过的题数或新增法律知识量。另项记录 T057 的 valid 对旧 train 泄漏为 0，该项按去掉 system 的对话键核查。复算不符先检查文件与计数口径。全程只读历史资产和 `datasets/latest`。
2. **先串行采集 P 和 C。** 记录原服务状态和 `artifacts/serve/current.json`，确认端口 8080 可用。先用 `uv run tu serve model --exp exp-20261116-resume500` 启动 P，再对 C 使用 `uv run tu serve model --exp exp-e003-7b-epoch2`。两次均按同一顺序操作：核实监听进程、启动参数与 current 中的 exp；就绪后运行 `uv run python scripts/experiments/e002/ab.py 0`，保存同题、同 prompt、温度 0 下 `default_model` 与基座全名的路由及输出；执行第 3 节对应的十题评测，保存完整 run；停止本次服务、查端口和 MLX 内存释放后再切换。若无法区分路由，先查进程和权重再换题复核。P 启动前留存实际评测源码（含编排、引用校验、运行器和指标）的文件清单与内容哈希，以及实际 `build_system_prompt(5)` 的 UTF-8 文本哈希。从 P 至 V 锁定这些内容、用例版本、温度与端点。每次启动 P、C、H、V 评测前分别复核并登记源码与 prompt 哈希；若有偏离，恢复已登记版本、核对通过后再运行。
3. **P、C 完成后直接训练一个完整 epoch。** 新建 `configs/train/demo-7b-t075.yaml`。将 `data` 写为 `artifacts/datasets/ds-kb-20261119-045641-8247`，`resume_adapter_file` 写为 **`artifacts/train/exp-20261116-resume500/adapters/adapters.safetensors`**。选用全新未占用的固定 exp_id（建议 `exp-t075-7b-article-01`）。按 C 的实际 `mlx_config.yaml` 对齐 batch=1、seq=2,048、`grad_checkpoint: true`、`mask_prompt: true`、LoRA rank=8/scale=10/dropout=0/num_layers=-1、记录字段 alpha=16、seed=43、学习率 5e-5、warmup=100、每 500 步存档、50 步报训练、200 步验证、每次 25 个验证 batch。C 的 iters 与余弦衰减参数为 8,921，本轮二者为 8,962，相差 41 步。两者各自在对应数据集上走一轮，由同一父权重重新开始 Adam 与学习率调度。

   ```sh
   uv run python scripts/run_training_guarded.py configs/train/demo-7b-t075.yaml artifacts/logs/t075/01/guard.log
   ```

   先建立日志目录，接电并预留约 2 GB 训练产物空间（历史同规模目录约 1.4 GiB）。guard 调用 `caffeinate -is` 与带 fp32 注意力、NaN 守卫的项目训练入口，设置 `HF_ENDPOINT=https://hf-mirror.com` 和 `HF_HUB_DISABLE_XET=1`。推理也使用已核实的本机快照，避免模型版本漂移。训练期间独占本机计算资源。历史 8,421 步耗时 13.8 h，8,921 步耗时 12.3 h；此次有较长的文章样本，**建议留 14–16 h 连续训练窗口，冒烟和评测另计**。记录实际进度、验证 loss、守卫跳步及 ETA。[训练封装](../../src/tu_assistant/train/mlx_train.py) · [守卫启动器](../../scripts/run_training_guarded.py)
4. **确认实际完成再起推理。** detached 启动返回 0 只表示已拉起；`tu train` 也只打印子进程返回码。直接核实新实验 `manifest.json.returncode == 0`、日志确实到 8,962/8,962、末次训练及验证 loss 有限、守卫无异常终止，且 `adapter_config.json` 与最终权重均存在。用 `uv run python scripts/check_safetensors_finite.py <最终权重>` 查到张量且全部有限，登记 hash。若中断，保留本次目录和健康 checkpoint，排明原因；恢复需新 exp_id。只载权重会重置优化器和采样顺序，单纯把两段步数相加无法证明完整跑过一轮。推荐从同一父权重重新跑完整一轮，额外长训单独确认窗口。
5. **最终权重核验通过后立即做 H、V 和对账。** 用 `tu serve model --exp` 切到新实验，先按第 2 步做 A/B 冒烟，再依次运行 H 和 V，执行下文 SC-016 双重判定。对四个 run 分别核对 `config.exp`、`config.base_model`、`config.model=default_model`、`inputs.kb`、`inputs.cases`、system prompt 已启用、`gold_clause_issues=[]`、条数与逐题 ID。参数 `--exp` 用于记录，实际 adapter 由服务进程加载。结束时只关闭本次启动的进程并恢复先前的服务状态。重试使用新的实验或 run 目录，留存失败证据。

## 4. 怎样判断文章是否学到了

在实验记录中为 P、C、V 各保留未经校验的 `final_raw` 和实际交付的各轮 `turns[].content`。同题配对列出 V−P（候选相对于父模型的总变化）、C−P（在旧数据上多训一轮的变化）和 V−C（改用 T057 数据续训相对旧数据续训的差异），写明分母及改善、持平、退步的题号。

- **出稿与拒答。** 9 道设 `expect_articles` 的题逐题核对期望和实得篇数，记录完全符合题数 / 9；分别看默认多篇、指定篇数与多轮修改。article-007 单列自动拒答初筛和项目方依 rubric 给出的正确/错误判定，按下表处理分歧。SC-008 范围内误拒、SC-011 的未泄露篇数/可评篇数、标注题覆盖和未拆篇泄露分别列示。若分母为零，写明缺少可评交稿。
- **法律正确性、多样性与修改。** 将 10 题的原 rubric 与 P/C/V 三份交付稿按题并排交项目方评审，记录分母、判定与依据。SC-009 按篇核对场景事实、责任主体、引用要件；SC-010 按同题同轮的多篇稿查看是否实质重复。article-008 核对通俗改写同时保留案情和依据，article-010 核对换背景后的事实、依据和保护名称。自动篇数和引用存在性无法给出这些语义结论。按已评/待评分别登记，人工意见到位后才能报告相应增益。
- **结论范围。** 新 train 中 96.5% 的行在旧 train 有相同对话。C 与 V 均从 P 续训，并对齐 seed 和主要超参，但数据构成、样本顺序与长度、总训练步数和余弦衰减长度均有差异。T057 同时更换了 67 条关系样本、调整拒答等配比，文章素材覆盖的六部法规又缺少 v1 多题涉及的《劳动法》《劳动合同法》。C−P 与 V−C 可以帮助判断观测差异更接近重复训练还是更换数据后的表现；单次种子、十题对照无法单独量化文章样本的因果贡献。各项 SC-001～SC-015 继续对照规格目标值。

**事前登记的演示换模条件。** 仅以第 8,962 步最终 adapter 参加 H、V，其他 checkpoint 仅供故障恢复。H 的两道硬门槛须全部通过；再按下列三项检查 V。比较对象固定为 P，C 用于解释差异。文章部分采用相对门槛和项目方审稿，无另设的绝对文章分数线。

| 候选须同时满足 | 判定证据 |
|---|---|
| V 的篇数完全符合题数 ≥ P | 对两边同 9 题统计 `scores.article_count.ok` 为真的题数，给出两个分子和共同分母 9。 |
| article-007 的 V 拒答结果 ≥ P | 由项目方按同一 rubric 核对 P、V 交付文本，比较人工终判（正确 1、错误 0）。逐份保留自动原判 `scores.refusal_correct` 及 `refusal_evidence`、人工原判、引用的文本与对应评分要点。两者分歧时写明原因，以人工终判参与换模判定；人工待评则本项待定。 |
| 项目方完成 V 十道文章题评审且未指出实质性法律错误 | 按题记录审阅结论与理由，尤其覆盖法律依据、构成要件和责任主体。评审未完标为待定，继续使用父模型。 |

H 通过且三项文章条件全部满足，最终 adapter 才具备换模资格。**若三项与 P 全部持平，项目方逐题评审也未发现可见文章增益，默认继续用 `exp-20261116-resume500` 演示**，同时登记评审依据，用户可另行决定。若出现可见改善，列明题号和 rubric 证据，提交用户考虑换模。任一条件失败也保留父模型，登记失败项与题号。候选始终使用第 8,962 步最终权重。

## 6. 已确认的实施安排

1. **执行顺序。** 用户已确认立即实施。依次运行 P、C，确认推理服务退出后直接开训；最终权重通过健康检查后接续 H、V 和对账。完整训练预计 14–16 小时，各阶段实际起止时间以日志为准。
2. **评测范围。** 按 P/C/H/V 四份 run 执行，C 直接用已训练好的 E003 权重，增加一次 10 题推理。
3. **换模规则。** 按第 4 节执行：最终权重先过 H 双门槛，再核对篇数、article-007 的人工终判和实质法律错误评审。三项全持平且未见文章增益时默认保留父模型，用户可另行决定；人工待评或任一条件失败时继续以父模型演示。
