# 01 全局视角：我们要训练一个什么样的模型

本章回答三个问题：大模型是怎么"知道"东西的？让它掌握我们的法律文档有哪些办法？本项目为什么选现在这条路？

---

## [L1.1] 大模型是什么

大语言模型（LLM）本质上是一个**预测下一个字的函数**：给它一段文字，它算出"下一个 token 最可能是什么"，
把这个 token 接到末尾，再预测下一个，如此循环就生成了一段回答。

- **token**：模型读写文字的最小单位。中文里大约 1–2 个字是一个 token。
- **参数**：模型内部的数字（权重）。7B 模型有约 70 亿个参数。训练就是不断调整这些数字，让预测更准。
- **预训练**：模型厂商用数万亿 token 的通用文本训练出"基座模型"。基座模型已经会说话、会推理，也懂一些法律常识，
  但不知道我们手里这 24 篇文档的具体内容。

可以把参数理解为**对训练数据的有损压缩**：模型见过的内容以某种分布式的方式"存"在参数里，
但它不是数据库，不能保证逐字复原。这一点是后面所有设计的出发点。

## [L1.2] 让模型掌握私有知识的三种方式

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **放进提示词**（上下文） | 每次提问时把相关文档全文塞给模型 | 最简单；原文准确 | 文档多了塞不下；每次都要处理大量文字，慢且贵 |
| **RAG**（检索增强生成） | 先从文档库里检索出相关段落，再交给模型回答 | 文档更新即生效；可以给出原文出处 | 检索不准就答不准；依赖检索系统 |
| **微调**（把知识训进参数） | 用文档内容训练模型，改变它的参数 | 模型"本身"就懂；不依赖外部检索；部署简单 | 记不准原文细节；文档更新要重训 |

三者不互斥，正式产品里经常组合使用。

## [L1.3] 微调的几种形式

| 名称 | 全称 | 训练数据长什么样 | 教会模型什么 |
|---|---|---|---|
| **CPT** | Continued Pre-Training，继续预训练 | 大段纯文本 | **知识**：让模型"读"新领域的文字 |
| **SFT** | Supervised Fine-Tuning，指令微调 | "问题 → 标准回答"的对话 | **行为**：怎么回答、什么格式、什么时候追问 |
| **DPO** | Direct Preference Optimization，偏好优化 | 同一问题的"好回答"和"坏回答"成对 | **取舍**：少犯某类错误，比如编造条款号 |

本项目 POC 只做 **SFT**，但训练数据里既有知识类样本（"第 N 条讲什么"），也有行为类样本（多轮追问、普法文章），
相当于用一次训练同时教知识和行为。正式阶段再拆成 CPT + SFT 两步，必要时加 DPO。

## [L1.4] 知识难训，行为好训

这是微调最重要的一个经验：

- **行为**（格式、语气、流程）很容易通过 SFT 学会，几百到几千条样本就有明显效果。
- **知识**（具体的条款号、原文、数字）很难精确地训进参数。研究发现，同一个知识点如果只以一种说法出现几次，
  模型基本记不住；要用**多种不同表述**反复出现（换句式、问答、正反向提问），模型才能在被问到时"提取"出来。

所以我们的训练数据会把每个条款改写成多种问法（见第 04 章），并且不完全依赖模型的记忆（见 L1.6）。

## [L1.5] 本项目为什么选"把知识训进模型"

项目方的本质需求有两条：

1. **私有部署**：模型运行在自己的环境里，数据不出去；
2. **模型本身学过这些文档**：是"自己的模型"，而不是一个通用模型外挂检索。

微调直接满足这两点。代价是 L1.2 表里说的"记不准原文细节"——在法律场景里，这是不能接受的，所以需要 L1.6 的补救。

## [L1.6] 出处校验层：给模型的记忆兜底

模型回答时，必须用固定格式标注每一处引用，例如：

```
〔《中华人民共和国工会法》（2021年修正）第五十一条第一款〕
> （条款原文）
```

模型输出后，一段**普通程序**（不是模型）逐个检查这些引用：

| 检查结果 | 处理 |
|---|---|
| 编号存在、原文一致 | 保留 |
| 编号存在、原文有出入 | 用条款库里的原文替换 |
| 编号不存在 | 删除这段引用，标注"未通过校验" |

这样交付给用户的条款原文 **100% 准确**。但要注意它的局限：如果模型引用了一个真实存在、但**并不适用**的条款，
校验层发现不了——这只能靠评测（第 06 章）来发现。

> 校验层是按编号"查表"，不是检索：它不帮模型找答案，只负责核对模型给出的答案。

## [L1.7] 整个系统的流程

```
                  ┌──────────── 离线（开发阶段） ────────────┐
  24 篇法律文档 → 入库与条款切分 → 条款库 ──→ 合成训练数据 → 训练（SFT）→ 自训模型
                                  │                                        │
                                  │           ┌──── 运行时（用户使用） ────┘
                                  ↓           ↓
  用户提问 → 对话编排（追问、确认意图）→ 自训模型生成回答 → 出处校验层 → 交付给用户
```

- 外部大模型（如 DeepSeek）只出现在左上角"合成训练数据"这一步，只处理公开的法律文档。
- 运行时整条链路都在本机，用户的对话内容不会发到外面。

## [L1.8] POC 能说明什么、不能说明什么

| POC 能说明 | POC 不能说明 |
|---|---|
| 入库 → 合成 → 训练 → 评测 → 对话的全流程能跑通 | 文档增加到约 1000 篇时效果会怎样 |
| 多轮追问、普法文章等交互体验是否成立 | "训进参数"和"检索"哪个更好（没有对照组） |
| 出处校验能保证交付的条款原文准确 | 模型效果的上限（POC 不追求效果） |
| 小规模下模型能记住多少（校验前的引用准确率） | |

规模越大，模型要记的东西越多，记错的概率越高。所以 1000 篇的结论必须在正式阶段单独验证。
