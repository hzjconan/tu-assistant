## L3.1 法律文本的结构

中国法律法规的文本是有固定层级的：

```
第X编 / 第X章 / 第X节        ← 组织结构，不是可引用内容
第X条                        ← 最基本的引用单位（"条"）
  （条内自然段）              ← "款"，第 1 款是紧跟条号的那段
  （一）（二）（三）           ← "项"，款里的并列细目
```

例子（自编的样例，下同）：

```
第三条 企业应当依法建立工会组织：     ← 第 3 条第 1 款（引言）
（一）职工二十五人以上的……；          ← 第 3 条第 1 款第 1 项
（二）不足二十五人的……。              ← 第 3 条第 1 款第 2 项
```

为什么要拆到款、项？因为 spec FR-006 要求引用"精确到条，有款、项时精确到款、项"。
如果只按条存，校验层就没法判断模型引用的"第三条第一项"是不是真的有这项。

## L3.2 条款切分

切分器 `kb/parse.py` 是纯粹的**规则程序**（正则 + 状态机），不用任何模型：

- 行首匹配 `第X编/章/节` → 记入"标题路径"（每条款都带上它所在的章节）；
- 行首匹配 `第X条` → 开始新条款；
- 条款内每一行 → 新的一款；
- 行首或行内的 `（N）` → 项（并入当前款再拆出来，所以项归属正确的款号）；
- 完全没有 `第X条` 的文件（如通知类），退而用 `一、二、` 分段。

中文数字是另一块：`第五十一条` → 51、`（三）` → 3，由 `kb/numbers.py` 转换。
边界情况都写了测试：`十`→10、`一百零一`→101、`一百一十`→110。

> 为什么不用大模型切分？切分是**确定性工作**——同一个文件每次结果必须一样，
> 且要逐字保留原文。这正是"能确定性完成的事交给程序"的体现（research R6）。

## L3.3 知识库版本与 SQLite

- 每次入库生成一个新文件 `artifacts/kb/kb-<时间戳>.sqlite`，就是知识库的一个版本。
- 训练和评测都引用具体的 kb_version，保证可复现（原则 VI）。
- POC 采用"整批重导"：文档变了就全部重新导入生成新版本，不做增量更新
  （24 篇的规模几秒就跑完；增量更新留给正式阶段）。
- 唯一权威：同一标题最多一个 `status=current`，校验层默认查现行版本。

## L3.4 条款关联（ClauseRelation）

法规里"什么算违法"和"怎么罚"通常不在同一条。规则抽取 `kb/relations.py`
扫描条款原文中的明文引用：

- `违反本法第X条（规定）` → liability_for（本条款是第 X 条的法律责任）
- `第X条所列` → liability_for
- `第X条除外` → exception_of
- `依照/按照/依据第X条` → references

方向约定：**from = 被引用的条款，to = 含有该引用的条款**。
这样模型引用了条款 A，就能查"还有没有已确认的关联条款该补上"。

抽出来的是**候选**（`confirmed=false`），需要人工逐条确认才生效——
因为规则会把"真关联"和"只是碰巧提到"混在一起。
本批语料最初抽出 35 条候选（旧库 `kb-20261113-093057`）；经 T077 修正抽取规则与 T019 两批人工审阅后，新派生库 `kb-20261119-045641` 共确认 **67 条**关联（`liability_for` 26 条 + `references` 41 条；累计撤销旧错边 10 条），审定源文件全部归档在 `data/relation-reviews/` 以便从 git 完整重建。两类关系的审阅口径有明显差异：`liability_for` 严格要求 `to` 规定违法法律责任且与 `from` 构成要件对齐；`references` 不要求存在违法行为，只要 `to` 实质援引了 `from` 这一款的实体情形、计算标准或程序（如合法解除劳动合同触发经济补偿）即成立，但整条展开中与援引语境无关的款（如优先录用、档案备查）仍须人工剔除。

### [L3.4.1] 条与款的定位粒度：抽取、审阅与校验如何联动

在 T052 普法文章复审中，我们发现旧库 12 对已确认的 `liability_for` 里有 **6 对错款**，根因是**编号、抽取、审阅、校验四层各自做了隐含假设，叠在一起把错放大了**：

1. **真实案例（错款 vs 整条展开）**
   - **错款**：《上海市集体合同条例》第三十八条明写“违反本条例第十条第二款规定……”，但旧规则只截到 `第十条` 并默认落到最小款号 `p1`，把本属于第十条第 2 款（协商代表履职保护）的罚则挂到了第十条第 1 款（工作时间视同正常劳动）。
   - **整条覆盖**：同一法规第四十条写“违反本条例第二十一条……”，而第二十一条共有 3 款（第 2、3 款还各含 4 项具体禁止行为）。旧规则只建了 `a21:p1 → a40:p1`，漏掉了最核心的第 2、3 款。
2. **三层联动修复（T077）**
   - **编号层（`kb/parse.py` & `kb/derive.py`）**：全库 1,663 条中有 787 条为多款条文。旧版把第 1 款写成“第N条”，导致训练样本把“第N条”教成了“仅第一款原文”。新 KB 从旧 SQLite 派生（保留 `clause_id` 与原文零变化、历史库只读不动），将多款条文第 1 款及其子项显式标为 `第N条第1款`；单款条文（含单款含多项）仍写 `第N条`。
   - **抽取与审阅层（`kb/relations.py` & `tu kb relations review/confirm`）**：规则扩展到捕获款/项、并列（`、` / `和`）与区间（`至`），遇到整条引用多款条文时**按款展开**为多条候选，由人工逐款剔除总则/宣示性条款（例如《工会法》第三条第 2 款是工会职责宣示，不属于第五十一条“阻挠入会”的罚则范围，经人工 `reject` 剔除）；审阅界面展示含子项的完整原文、总款数与触发片段，确认入口改为事务化四态差异导入（`confirm` / `revoke` / `reject` / `pending`），并拒绝修改历史只读库。
   - **校验层与下游去重（`citation/verify.py` / `eval/metrics.py` / `chat/orchestrator.py`）**：
     - 修复“单款含多项”只写条号被误判 `incomplete` 的问题；
     - 对多款条文未写款号的引用采取**兼容款级（口径 C）**：新样本一律写款号，但校验层保留“引文逐字唯一匹配某款即落回该款”的回退，并用 `fallback_para_matches` 单独计数，保证新旧模型可比；
     - 整条按款展开后多款共享同一责任条款时，SC-005 与编排层系统补充块均按去重后的责任条款计分/追加，避免分母膨胀或重复输出。

## L3.5 出处校验层

模型输出里每处引用写成固定标记：

```markdown
〔《文件全称》（版本）第N条第M款第K项〕
> 条款原文
```

校验层 `citation/verify.py` 对每处引用做查表，四种结论：

| 结论 | 含义 | 交付给用户的结果 |
|---|---|---|
| `ok` | 编号存在且原文一致 | 原样保留 |
| `corrected` | 编号存在但原文写错 | 替换成知识库原文 |
| `not_found` | 编号不存在 | 整块删掉，替换为"此处引用未通过校验，已删除" |
| `incomplete` | 裸引用（只写了"第X条"没有完整标记）或编号不够精确 | 保留文本，记为出处不完整 |

几个细节：

- **省略原文会自动补入**——模型只写标记不写 `> ` 原文时，校验层补上库里的原文；
- **版本写错**（如把 2021 写成 1999）→ 按现行版本兜底并修正版本号；
- **"第N条第M款"包含项**——比对原文 = 该款引言 + 所有项的拼接；
- **单款条文（无论是否含多项）只写"第N条"** → 无歧义直接定位到该唯一款（自动拼接各项）；
- **多款条文只写"第N条"** → 无引文或引文不匹配时判 `incomplete`；引文逐字唯一匹配某款时触发兼容回退并单独计数（见 [L3.4.1]）；
- **准确率分两层**：校验前（模型真实记住多少）和校验后（恒为 100%）。
  前者才是判断"知识训进参数"成效的关键指标。

**局限**：模型"编号真实存在但引错了条"（比如该引第 4 条却引了第 5 条）
校验层拦不住——编号、原文都是真的，只是用错了地方。这只能靠评测发现。

## L3.6 语料准备过程与真实入库数据

语料不是"拿过来就导"，先过了一轮人工筛选。完整过程：

| 步骤 | 文件数 | 说明 |
|---|---|---|
| 项目方提供 | 28 | 精简后的纯文本，约 1.0MB |
| − 1 篇重复文件 | 27 | 《上海市集体合同条例》出现两份内容相同的文件，留一份 |
| − 1 篇合同范本 | 26 | 《上海市集体合同参考文本（企业版）》是合同模板不是法规 |
| − 1 篇《民法典》 | 25 | 体量占全库约 1/3 且大部分内容与工会场景无关（见下） |
| − 1 篇社保衔接《通知》 | 24 | 新农保/城居保制度衔接文件，非工会领域 |
| **入库** | **24** | `inputs/excluded/` 保留全部排除文件，可逆 |

`tu kb import inputs/project/001` 的实际结果（kb-20261113-093057）：

| 指标 | 数值 |
|---|---|
| 条款行数 | 3,809 条（款/项级） |
| 校验问题 | 24 个（全部是元数据类，无切分错误） |
| 规则抽取并确认的关联 | 35 条 |

处理过的情况：

- **1 个特大文件被排除**：民法典单篇切出 2,136 条款行（占全部 1/3），
  且大部分内容（物权、婚姻继承等）与工会咨询无关。继续留着会稀释
  小模型的训练信号、造成引用偏置，经项目方决定移出知识库。代价是
  遇到民法典问题会拒答——这属于设计内的行为（不支持的领域必须拒答）。
  这里学到的判断："该不该进知识库"看的不是它是不是法律，而是
  **它会不会出现在用户的问题里**。民法典是法律没错，但工会咨询几乎
  用不上它，留着弊大于利。
- **同名文件**：3 个文件解析出同名——其中 2 个是同一法规的重复文件
  （删 1 个），另 1 个实为合同范本，不是法规，移出知识库（见下）。
- **日期提取**：多数文件的日期在开头 10 行内、一行可能有多个修订日期，
  取最新一个；也有文件日期在末尾几行（如保障农民工工资支付条例），
  所以首尾都要扫；缺版本标识的用发布日期推断（`version_inferred`）。

**合同范本为什么不留**：集体合同参考文本是合同模板不是法规——模型若把它
当法律依据引用会误导用户，且它的内部结构不按"第X条"组织。判断依据是
文件的性质而不是文件名，所以这类文件要在入库前人工剔除。

**非工会领域文件为什么不留**：社保制度衔接通知内容真实合法，但与工会
咨询主题无关。它的危害比合同范本市隐晦——不会引用错，但占训练数据、
占模型容量，还会让模型对"范围外问题该不该拒答"的边界学模糊。

## L3.7 踩过的坑

1. **（一）（二）项行被当成新的一款**：最初每条项行都递增款号，
   导致 `第3条第1款第1项` 变成 `p2:i1`。修复：项行并入当前款再拆。
2. **只写"第N条"查不到**：库里存的行都有款号（≥1），裸"第N条"匹配失败。
   修复：校验层对"整条引用"做聚合解析（单款无项才精确解析，否则 incomplete）。
3. **中文数字下标错位**：`_CN_NUM` 以"零〇"开头导致 `第〇项`。
4. **typer 单命令陷阱**：只有一条子命令时 `tu version` 被当成多余参数，
   需要显式加 callback 保持子命令结构。
5. **文件名没有版本信息**：元数据推断全靠文件名与文件头启发式，
   全部文件缺版本标签——元数据补充机制需要项目方配合。
6. **括号条旨被误切为第 1 款（T078）**：T019 第二批人工审阅时发现，
   《上海市工伤保险实施办法》每条首行带括号小标题（如 `第二十七条（鉴定程序）`），
   切分器把它切成了 `p1`，导致该文件 63/63 条的款号整体顺延 +1（例如“第一款第二项”落到了 `p2:i2`）。
   全库 24 篇仅此 1 篇受影响，因涉及 5 道 v1 评测题，已登记为 T078 单独评估修复。
