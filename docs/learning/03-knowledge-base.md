## L3.1 法律文本的结构

中国法律法规的文本是有固定层级的：

```
第X编 / 第X章 / 第X节        ← 组织结构，不是可引用内容
第X条                        ← 最基本的引用单位（"条"）
  （条内自然段）              ← "款"，第 1 款是紧跟条号的那段
  （一）（二）（三）           ← "项"，款里的并列细目
```

例子（自编的样例，下同）：

```
第三条 企业应当依法建立工会组织：     ← 第 3 条第 1 款（引言）
（一）职工二十五人以上的……；          ← 第 3 条第 1 款第 1 项
（二）不足二十五人的……。              ← 第 3 条第 1 款第 2 项
```

为什么要拆到款、项？因为 spec FR-006 要求引用"精确到条，有款、项时精确到款、项"。
如果只按条存，校验层就没法判断模型引用的"第三条第一项"是不是真的有这项。

## L3.2 条款切分

切分器 `kb/parse.py` 是纯粹的**规则程序**（正则 + 状态机），不用任何模型：

- 行首匹配 `第X编/章/节` → 记入"标题路径"（每条款都带上它所在的章节）；
- 行首匹配 `第X条` → 开始新条款；
- 条款内每一行 → 新的一款；
- 行首或行内的 `（N）` → 项（并入当前款再拆出来，所以项归属正确的款号）；
- 完全没有 `第X条` 的文件（如通知类），退而用 `一、二、` 分段。

中文数字是另一块：`第五十一条` → 51、`（三）` → 3，由 `kb/numbers.py` 转换。
边界情况都写了测试：`十`→10、`一百零一`→101、`一百一十`→110。

> 为什么不用大模型切分？切分是**确定性工作**——同一个文件每次结果必须一样，
> 且要逐字保留原文。这正是"能确定性完成的事交给程序"的体现（research R6）。

## L3.3 知识库版本与 SQLite

- 每次入库生成一个新文件 `artifacts/kb/kb-<时间戳>.sqlite`，就是知识库的一个版本。
- 训练和评测都引用具体的 kb_version，保证可复现（原则 VI）。
- POC 采用"整批重导"：文档变了就全部重新导入生成新版本，不做增量更新
  （28 篇的规模几秒就跑完；增量更新留给正式阶段）。
- 唯一权威：同一标题最多一个 `status=current`，校验层默认查现行版本。

## L3.4 条款关联（ClauseRelation）

法规里"什么算违法"和"怎么罚"通常不在同一条。规则抽取 `kb/relations.py`
扫描条款原文中的明文引用：

- `违反本法第X条（规定）` → liability_for（本条款是第 X 条的法律责任）
- `第X条所列` → liability_for
- `第X条除外` → exception_of
- `依照/按照/依据第X条` → references

方向约定：**from = 被引用的条款，to = 含有该引用的条款**。
这样模型引用了条款 A，就能查"还有没有已确认的关联条款该补上"。

抽出来的是**候选**（`confirmed=false`），需要人工逐条确认才生效——
因为规则会把"真关联"和"只是碰巧提到"混在一起。
本批 28 篇文档抽出了 72 条候选，等你确认（T019）。

## L3.5 出处校验层

模型输出里每处引用写成固定标记：

```markdown
〔《文件全称》（版本）第N条第M款第K项〕
> 条款原文
```

校验层 `citation/verify.py` 对每处引用做查表，四种结论：

| 结论 | 含义 | 交付给用户的结果 |
|---|---|---|
| `ok` | 编号存在且原文一致 | 原样保留 |
| `corrected` | 编号存在但原文写错 | 替换成知识库原文 |
| `not_found` | 编号不存在 | 整块删掉，替换为"此处引用未通过校验，已删除" |
| `incomplete` | 裸引用（只写了"第X条"没有完整标记）或编号不够精确 | 保留文本，记为出处不完整 |

几个细节：

- **省略原文会自动补入**——模型只写标记不写 `> ` 原文时，校验层补上库里的原文；
- **版本写错**（如把 2021 写成 1999）→ 按现行版本兜底并修正版本号；
- **"第N条第M款"包含项**——比对原文 = 该款引言 + 所有项的拼接；
- **只写"第N条"而该条有多款多项** → 无法唯一定位，判 incomplete；
- **准确率分两层**：校验前（模型真实记住多少）和校验后（恒为 100%）。
  前者才是判断"知识训进参数"成效的关键指标。

**局限**：模型"编号真实存在但引错了条"（比如该引第 4 条却引了第 5 条）
校验层拦不住——编号、原文都是真的，只是用错了地方。这只能靠评测发现。

## L3.6 本项目的真实入库数据

`tu kb import inputs/project` 的实际结果（kb-20261113-071400）：

| 指标 | 数值 |
|---|---|
| 文件数 | 26 篇（原 28：1 篇重复删除、1 篇合同范本不入库） |
| 条款行数 | 5,953 条（款/项级） |
| 校验问题 | 27 个（全部是元数据类，无切分错误） |
| 规则抽取的候选关联 | 68 条 |

处理过的情况：

- **1 个特大文件**：单篇切出 2,136 条款行（占全部 1/3），确认是独立
  长法规（民法典），不是汇编，不用拆；但训练数据均衡抽样时要限制它的占比。
- **同名文件**：3 个文件解析出同名——其中 2 个是同一法规的重复文件
  （删 1 个），另 1 个实为合同范本，不是法规，移出知识库（见下）。
- **日期提取**：多数文件的日期在开头 10 行内、一行可能有多个修订日期，
  取最新一个；缺版本标识的文件用发布日期推断版本号（`version_inferred`）。

**合同范本为什么不留**：集体合同参考文本是合同模板不是法规——模型若把它
当法律依据引用会误导用户，且它的内部结构不按"第X条"组织。判断依据是
文件的性质而不是文件名，所以这类文件要在入库前人工剔除。

## L3.7 踩过的坑

1. **（一）（二）项行被当成新的一款**：最初每条项行都递增款号，
   导致 `第3条第1款第1项` 变成 `p2:i1`。修复：项行并入当前款再拆。
2. **只写"第N条"查不到**：库里存的行都有款号（≥1），裸"第N条"匹配失败。
   修复：校验层对"整条引用"做聚合解析（单款无项才精确解析，否则 incomplete）。
3. **中文数字下标错位**：`_CN_NUM` 以"零〇"开头导致 `第〇项`。
4. **typer 单命令陷阱**：只有一条子命令时 `tu version` 被当成多余参数，
   需要显式加 callback 保持子命令结构。
5. **文件名没有版本信息**：元数据推断全靠文件名与文件头启发式，
   28 篇全部缺版本标签——元数据补充机制需要项目方配合。
