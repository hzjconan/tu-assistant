# 第 5 章 训练：一次训练的全过程、超参数与 loss 曲线

> 对应任务：Phase 2/3 的 T032（`tu train`）。代码在 `src/tu_assistant/train/mlx_train.py`，
> 配置在 `configs/train/`。本章所有数字来自第一次完整训练
> `exp-20261114-120250`（1.5B 调试模型）的真实日志与清单。
> 先说结论：**这次训练"跑得很顺利"，但模型基本没用**——评测里条款召回率是 0。
> 这正好是一个很好的教学反例，完整排查过程见

## L5.1 一次训练的全过程

一句命令：

```bash
uv run tu train --config configs/train/debug-1.5b.yaml
```

背后发生了这几步（`train/mlx_train.py:run_training`）：

```text
configs/train/debug-1.5b.yaml          ← 我们写的"项目配置"（人看的）
  │  1. 读配置；生成实验 ID：exp-<UTC 时间戳>
  │  2. 数 train.jsonl 行数，把 epochs 换算成 iters
  │     iters = 训练样本数 × epochs ÷ batch_size = 14,493 × 2 ÷ 1 = 28,986
  ▼
artifacts/train/<exp>/mlx_config.yaml  ← 翻译成 mlx_lm 认识的配置
  │  3. 子进程运行：python -m mlx_lm lora -c mlx_config.yaml
  │     输出全部写进 train.log
  ▼
mlx_lm lora：加载 4bit 基座 → 给指定层挂 LoRA 旁路 → 循环训练
  │  每 50 步报告一次 train loss，每 200 步算一次 val loss
  ▼
artifacts/train/<exp>/adapters/adapters.safetensors   ← 产物：约 21MB 的适配器
artifacts/train/<exp>/manifest.json                   ← 清单：配置、种子、耗时、返回码
```

几个要点：

- **基座不动，只产出适配器**。1.5B 4bit 基座约 1GB 放在 Hugging Face 缓存里，
  训练只得到一个 21MB 的 `adapters.safetensors`（LoRA 原理见 [L2.3]）。
  推理时 `tu serve model --exp <exp>` 把"基座 + 适配器"一起加载。
- **为什么要换算 iters**：mlx_lm 不认"轮数"，只认"走多少步"。一步（iteration）
  处理一个 batch；batch=1 时一步就是一条样本，所以 2 轮 = 28,986 步。
- **清单（manifest）**：谁、用什么数据、什么配置、种子多少、跑了多久，全部可复现
  （宪章原则 VI）。本次 `duration_s = 14342`，即约 **3 小时 59 分**
  （本地时间 2026-11-14 20:02 启动，11-15 00:01 保存适配器）。

日志开头会打印这样一行，值得认识：

```text
Trainable parameters: 0.342% (5.276M/1543.714M)
```

意思是：1.5B 模型共 15.44 亿参数，本次真正被训练的只有 527.6 万个（LoRA 旁路），
占 0.342%。其余 99.66% 是冻结的。

## L5.2 超参数逐项解释

超参数 = 训练前由人定下来、训练过程不会自己改的设置。本次真实值：

| 超参数 | 本次值 | 含义 | 本次的考量 / 事后看法 |
|---|---|---|---|
| base_model | Qwen2.5-1.5B-Instruct-4bit | 在哪个基座上微调 | 调试用小模型，先跑通流程 |
| epochs | 2 | 全部训练数据过几遍 | 1 轮常学不透，3 轮以上开始担心背死 |
| iters | 28,986 | 总步数（由 epochs 换算） | 见 L5.1 |
| batch_size | 1 | 每步同时喂几条样本 | 长样本多、内存有限，只能 1；代价是每步梯度很"抖" |
| learning_rate | 1e-5 | 每步参数改多少 | **偏保守**。LoRA 常用 1e-4 ~ 2e-4，1e-5 可能导致学得慢（E001 诊断 3） |
| lr_schedule | 无（恒定） | 学习率是否随训练衰减 | mlx_lm 默认不衰减 |
| max_seq_length | 2048 | 单条样本最多多少 token，超出截断 | 咨询类长回答需要较长窗口 |
| grad_checkpoint | 开 | 少存中间结果，用时间换内存 | 见 [L2.8]；长样本必开 |
| seed | 42 | 随机种子 | 固定后数据顺序、初始化可复现 |
| lora.num_layers | 16 | 给最后多少层挂 LoRA | 1.5B 共 28 层，只改了后 16 层 |
| lora.rank | 8 | LoRA 小矩阵的宽度 | 越大能学的越多，参数和内存也越多 |
| lora.scale | 10.0 | LoRA 旁路输出的放大倍数 | **mlx_lm 中真正生效的是它** |
| lora.alpha | 16 | 其他框架（PEFT）里的缩放写法 | **mlx_lm 不读取 alpha**，配置里写了也不生效 |
| lora.dropout | 0.0 | 训练时随机丢弃一部分旁路输出，防过拟合 | 数据量不大时常设 0 |
| val_batches | 25 | 每次算 val loss 用几个 batch | batch=1 时只抽 25 条验证样本，所以 val loss 很抖（L5.3） |
| mask_prompt | false（默认） | loss 是否只算 assistant 部分 | 默认连 user/system 文本也算进 loss |

几个值得多说两句的：

**学习率**是最敏感的超参数。太大：loss 乱跳甚至发散；太小：走得慢，
同样步数下学不到位。本次 loss 一直在降，但降得平缓，最终 val loss 0.79，
1e-5 偏小是怀疑对象之一。

**rank 与 scale**。LoRA 旁路是两个小矩阵 A（d×r）和 B（r×d），r 就是 rank。
旁路的输出要乘一个系数再加回主干：在 PEFT 等框架里这个系数是 `alpha / rank`
（本配置即 16/8=2）；而 mlx_lm 直接用 `scale`（本次 10）。
我们查过安装的 mlx_lm 源码（`tuner/utils.py`）：它只读 `rank / scale / dropout`，
写了 `alpha` 而没写 `scale` 会直接报错提示。所以本项目配置里的 `alpha: 16`
是个"死参数"，实际放大倍数是 10。

**num_layers 怎么算出 5.276M**。mlx_lm 默认给每层的 7 个线性层都挂 LoRA
（注意力的 q/k/v/o + 前馈网络的 gate/up/down）。每个线性层（输入 d_in、输出 d_out）
新增 `rank × (d_in + d_out)` 个参数。按 1.5B 的结构（hidden 1536、前馈 8960、
k/v 输出 256）算，每层 329,728 个，× 16 层 = 5,275,648 ≈ **5.276M**，与日志一致。

**mask_prompt=false** 意味着 loss 里也包含了"预测用户问题"的部分。用户问题是
外部模型生成的口语，模型本来就很难预测——这会让 loss 的绝对值偏高，
也让 loss 更不能直接代表"回答写得好不好"。

## L5.3 看懂 loss 曲线

**loss 是什么**：模型对"下一个 token 应该是什么"的猜测错得有多离谱。
训练样本里每个位置都有标准答案，模型给标准答案的概率越高，loss 越低。
粗略的直觉：loss ≈ 2.3 时模型平均在约 10 个候选里犹豫；loss ≈ 0.7 时约在 2 个候选里犹豫
（候选数 ≈ e^loss）。

**train loss 与 val loss**：

- **train loss**：在正在学的样本上的错误程度。日志每 50 步报告一次（这 50 步的平均）。
- **val loss（验证损失）**：在**从没训练过**的 valid 集样本上的错误程度，每 200 步算一次。
  它回答"学到的东西能不能推广到新样本"。

本次日志抽样（已剥离颜色码）：

| iter | train loss | val loss | 说明 |
|---:|---:|---:|---|
| 1 | — | 3.153 | 训练前：基座完全不懂我们的格式 |
| 50 | 1.793 | — | 头几十步下降最快：格式最先被学会 |
| 400 | 1.107 | 1.154 | |
| 1,000 | 1.041 | 0.917 | |
| 2,400 | 0.843 | 0.868 | |
| 5,000 | 0.806 | 0.813 | |
| 10,000 | 0.843 | 0.756 | |
| 12,800 | 0.807 | 0.852 | 中途 val 反而比 10,000 步高——抖动 |
| 20,000 | 0.714 | 0.925 | |
| 28,800 | 0.624 | 0.685 | |
| 28,986（结束） | 0.676 | 0.788 | 最终结果 |

怎么读这张表：

1. **前期陡降，后期平缓**：从 3.15 到 1.1 只用了几百步——这部分主要是
   "学会说话的样子"（引用标记、结构标题等高频固定格式）。之后两万多步只从
   ~0.9 降到 ~0.7，对应更难的"内容"部分。
2. **val loss 抖得厉害**：同一阶段相邻两次 val 可以差 0.2–0.3（例如 9,400 步 1.021、
   9,600 步 0.783；26,800 步 0.578、27,200 步 0.991）。原因是 `val_batches=25`、
   batch=1，每次只随机抽 **25 条** 验证样本，抽到长难样本就高、抽到短样本就低。
   看趋势要看一段区间的大致走向，不要盯单个点。
3. **train 与 val 差距不大**：最终 0.676 vs 0.788，没有出现"train 一路降、val 掉头上升"
   的过拟合形态（见 L5.5）。如果只看这张表，会觉得"训练很健康"。

**但评测结果是：条款召回率 0.000。** 下一节解释为什么。

## L5.4 loss 降了 ≠ 效果好（本次就是反例）

loss 衡量的是"在训练数据的分布上，逐 token 预测得准不准"。它和我们真正关心的
任务指标（引用对不对、条款找没找到）之间至少隔着三层：

1. **平均掩盖关键**：一条回答几百个 token，绝大部分是"根据……规定""违法行为认定"
   这类好猜的字；真正决定对错的是**文件名和条款号那十来个 token**。它们猜错，
   对平均 loss 的影响微乎其微。
2. **训练分布 ≠ 使用分布**：loss 是在 train/valid 上算的，而 valid 和 train 来自同一批
   合成数据、同样的格式。如果运行时的输入长得和训练数据不一样，val loss 再低也
   测不出来。本次正是如此：约 95% 的训练样本**没有 system prompt**，而运行时每次都带
   一段约 400 字的 system prompt（详见 E001 诊断 1）。val loss 测的是"不带 system
   prompt 时答得怎样"，评测测的是"带 system prompt 时答得怎样"——两件事。
3. **teacher forcing**：算 loss 时，每个位置都把"标准答案的前文"喂给模型，只问它下一个
   字；真正生成时，模型要接着**自己写的**前文往下写，一步写偏就会越偏越远
   （本次评测里有回答陷入"建议：……"无限重复，就是这种现象）。

**教训**：loss 只能说明"训练在正常进行"，不能说明"模型能用"。正确做法是
**尽早用小规模真实评测冒烟**——比如训练 1,000 步后就保存一个适配器，
跑 10 道评测题看看格式对不对，而不是等 4 小时训完才第一次看输出。

## L5.5 过拟合与欠拟合

| 形态 | loss 曲线表现 | 含义 | 常见对策 |
|---|---|---|---|
| 欠拟合 | train、val 都还偏高，且仍在下降 | 没学够：步数少、学习率小或模型太小 | 提高学习率、多训几轮、换大模型 |
| 正常 | train、val 同步下降并趋平，差距小 | 学到了能推广的东西 | — |
| 过拟合 | train 继续降，val 停滞后**上升** | 开始死记训练样本，对新样本变差 | 少训几轮、加 dropout、加数据、早停 |

本次属于哪种？train 与 val 差距小、val 还在缓慢下降，更像**轻度欠拟合**
（学习率 1e-5 偏小、2 轮未充分收敛）。但如 L5.4 所说，这个判断只关于"训练数据
分布上的表现"，解释不了评测为 0——评测失败的主因更可能在分布不一致和模型容量
（L5.6）。

一个本项目特有的矛盾：我们**希望**模型记住条款编号（某种意义上就是"背"），
而通常意义上的过拟合正是"背训练集"。区别在于：我们要它背的是"问题类型 → 条款号"
的对应，而不是背某条合成问法的原句。这也是为什么同一条款要合成多种问法（[L4.3]）。

## L5.6 模型规模与"容量"

**容量**：模型的参数能装下多少知识与能力。参数越多，容量越大。
LoRA 只训练很少的参数，它更像在原有能力上"纠偏"，而不是灌进全新的大量知识
（[L1.4] 知识难训，行为好训）。

### 我们要模型学的三层，难度递增

| 层 | 内容 | 例子 | 1.5B 本次表现 |
|---|---|---|---|
| 1. 格式与行为 | 〔〕引用块、"违法行为认定"结构、该追问时追问、范围外拒答 | 先输出〔《文件》（版本）第N条〕，下一行 `>` 原文 | **不稳**：学到了标题骨架，但 60 题中只有 5 题出现〔〕引用；追问与咨询混在一起 |
| 2. 条款定位 | 口语描述 → 正确的文件名 + 条款号 | "离职后多久不能去同行" → 对应的竞业限制条款 | **基本没学会**：召回率 0；还编造 KB 中不存在的文件 |
| 3. 原文逐字背诵 | 条款号 → 一字不差的原文 | — | **没学会**：引用块里的"原文"常是模型自己的分析句 |

### 换 7B 能帮上什么

- **更守规矩**：遵循长 system prompt、同时满足多条规则（引用格式 + 结构 + 追问上限）
  是大模型的明显优势，小模型常顾此失彼。第 1 层会更稳。
- **底子更好**：Qwen 预训练时读过大量中文法律文本，7B 记住的更多。
  对国家层面的法律，LoRA 往往只需要"纠偏 + 对齐格式"，不必从零教。
- **可训练参数更多**：同样 rank=8，LoRA 参数量随模型宽度增长。按两个模型的实际结构
  （7B：hidden 3584、前馈 18944、k/v 输出 512，同为 28 层）计算：
  - 同样只挂后 16 层：7B 约 **11.53M**，是 1.5B（5.276M）的约 **2.2 倍**；
  - `configs/train/demo-7b.yaml` 用的是 `num_layers: -1`（全部 28 层）：约 **20.19M**，
    约为本次 1.5B 的 **3.8 倍**。

### 换 7B 解决不了什么

- **逐字背 3,809 条原文，7B 也背不全**。纯 SFT 灌入大量逐字知识本来就是微调的弱项。
- **但本项目不要求第 3 层**：出处校验层（`src/tu_assistant/citation/verify.py`，[L1.6]）
  只要文件名 + 条款号对，就会用 KB 原文替换错误原文（corrected）、补全省略的原文。
  所以 7B 的目标是**第 1、2 层**。
- **第 2 层能否做好仍无保证**。"口语场景 → 条款号"本质上也是知识记忆，这是
  "纯 SFT、运行时不检索"路线的固有风险。7B 只是提高了概率。

### 代价

| 项 | 1.5B（本次实测） | 7B（估算 / 实测） |
|---|---|---|
| 训练时间 | 约 4 小时（2 轮，290–420 tok/s） | 约 **4–5 倍**（[L2.9] 7B 约 83 tok/s）；原计划"一到两晚" |
| 训练内存 | — | 长样本开梯度检查点峰值约 **11.5GB**（不开 23GB），32GB 机器可行 |
| 推理速度 | 快 | 更慢，演示时每次回答等待更久 |

### 兜底路线：RAG

如果 7B 的条款召回仍然很差，就说明问题不在模型大小，而在**路线本身**：
指望模型把"场景 → 条款号"全部记在参数里不现实。替代方案是 **RAG**（[L1.2]）：
运行时先从本地 SQLite 知识库检索相关条款原文，放进提示词，模型只负责分析。

这和合成训练数据时"把原文喂给 DeepSeek，让它照着写"（[L4.3]）是同一个思路——
**别让模型凭记忆，把材料摆在它面前**。检索全程在本机，不违反"数据不出本机"原则。
但它属于架构变更，需要回到 spec/plan 讨论后再做。

## L5.9 数值精度与注意力分数：一次 fp16 溢出事故实录

> 完整证据链见 [E001](../experiments/E001-1.5b-citation-failure.md)
> 尝试 4 的"NaN 根因诊断"与"续训后评测"。

### 现象

7B QLoRA 训练三次在同一个位置附近崩溃：无 warmup 时在 iter ~60–100，
有 warmup 时在 warmup 结束的 iter ~500——train/val loss 突然变成 `nan` 后再也没回来，
一次 NaN 梯度经 Adam 污染全部 LoRA 参数，之后 8,400 步全是空转。

### 机制：模型把"音量旋钮"拧到了精度天花板

1. **注意力分数决定"盯得多死"**。注意力先给每对 token 算一个相关度分数（logit），
   过 softmax 变成权重。分数整体放大，softmax 输出就更尖——几乎只看最高分的 token；
   分数小，权重就均匀分摊。
2. **我们的任务奖励"尖"**。模型要学"看到案情 → 逐字复述条款"。逐字复述需要
   生成每个字时死死盯住输入的特定位置，注意力越尖、复制越准、loss 越低。
   梯度下降于是持续奖励"把分数拧大"这个方向。
3. **没有刹车**。softmax 对平移不敏感只对缩放敏感，模型唯一能拧的就是放大倍数；
   LoRA 配置里没有约束 q/k 的衰减项；Qwen2.5 也没有 QK-norm（给 q、k 归一化的
   防爆设计）。于是分数一路涨：基座约 2,000–2,400 → iter 500 时 5,200–6,100。
4. **为什么偏偏最后一层**。最后一层的注意力输出直接喂给输出层，改动见效最快、
   梯度信号最强，LoRA 天然在这里学得最猛（第 27 层 `q_proj` 的 ΔW 范数约为
   中位数的 2.7 倍），分数先从这一层爆。
5. **撞上 fp16 的天花板**。激活默认 fp16（半精度，可表示范围约 ±65k）。分数 6,000+
   时，前向算 loss 还撑得住，**反向传播算梯度时中间量要在分数上再做指数/乘法**，
   直接溢出成 NaN。实测同一份 q/k/v：fp16 反向出数万 NaN，bf16/fp32 为 0。

### 两个容易误判的点

- **不是学习率的问题**。lr 只决定分数涨多快（无 warmup 约 100 步崩、有 warmup 约
  500 步崩），任务本身在奖励"拧大"这个方向，降 lr 只是推迟爆炸，治不了根。
  这正是"先别急着调超参，先找到真正的失败模式"的例证。
- **不是坏样本、不是 0 目标 token**。崩溃窗口的样本在基座上梯度全部正常；
  mask_prompt 下每条样本仍有 ≥8 个计 loss 的 token，无截断。排除法很重要：
  前一个排查把"基座前向有限"当成了证据，其实那只能排除"样本让前向 NaN"，
  排除不了"loss 计算的 0/0"或"反向溢出"。

### 我们的修复（训练侧三个补丁）

| 补丁 | 作用 | 定位 |
|---|---|---|
| **fp32 注意力** | 训练时把 `mx.fast.scaled_dot_product_attention` 包一层，q/k/v（及数组 mask/sinks）转 fp32 算完转回。只给溢出点换"高压管"，不全模型提精度（显存放不下） | 治本 |
| **NaN 守卫** | 梯度出现非有限值就把本步参数更新回滚（置零坏梯度 + `mx.where` 回滚＝跳步）并计数告警，一步白训代替全程白训 | 兜底 |
| **日志自动停训** | 包装脚本盯 train.log，iter/val 行出现 nan 立即 `killpg` 停训 | 省钱 |

三个补丁都只在**训练进程**内生效：前两个装在专用入口
`src/tu_assistant/train/patched_lora.py`（等价 `python -m mlx_lm lora`，
serve/chat/eval 不经过），第三个是独立启动器
`scripts/run_training_guarded.py`（自 detach + caffeinate + killpg 停训）。
注意训练循环的 step 在 `mx.compile` 内执行，守卫只能做惰性数组运算
（`mx.where` 回滚），不能做值依赖的 Python 分支——这是实现上的关键约束。

然后从 iter-500 检查点用 `--resume-adapter-file` 续训（只恢复权重，优化器状态
是新的，所以再配一小段 warmup）。

### 效果

修复**完全有效**：从 iter-500 检查点续训剩余 8,421 步，全程零 NaN、守卫零触发，
最终 adapter 392 个张量全部有限、最终 val loss 0.472——补丁把一次注定白跑
14 小时的训练救成了可交付产物。

但要分清楚：**补丁救的是训练稳定性，不是任务效果**。
~~续训后的评测显示引用指标与 iter-500 检查点几乎逐位一致（〔〕块 0/60、
条款召回 0、42/60 输出逐字相同）~~ **【2026-11-17 订正（E002）】**：
此前评测测的都是不带 adapter 的基座（见 L5.11），"逐字相同"是同基座
重测的必然。修复后重评的真实结果：训满版〔〕块 **60/60**、条款召回 **0.150**、
精确率 0.265；三个检查点召回 0.000（500 步）→ 0.083（约 4,500 步）→ 0.150
（8,921 步）。**【E002 §6 二次订正】**：不能把严格款级召回 0.150
直接归因为"记忆容量不足"。宽松解析下文件命中 45/60、条级命中 17/60
（基座仅 1/60），上海文件命中从基座的 0/22 升到 14/22；
但 gold 条款在 train 中位只曝光 2 次，容量与曝光还分不开，详见 E003。
这两个结果合在一起的完整教训是：先保证"训得完"（数值稳定），
再检验"训得对不对"（冒烟评测，且先确认测的是你的模型）——
前者是必要条件，后者才是结论。

### 教训沉淀

- **save_every 必须显式设置**：`mlx_train.py` 曾把缺省值写成总 iter 数（只在结束时
  存一次），中断即全损；这次正是 500 步检查点救回了整晚。
- **长任务与 agent shell 脱钩**：nohup/独立会话 + caffeinate + 接电源。
- **loss 健康 ≠ 权重健康**：发散前 loss 一路下降到 0.74，单看曲线毫无征兆；
  检查点权重可做有限性校验（392 个张量全部有限才可用）。
- **fp16 溢出是 4-bit 小模型的常见病**：激活精度不够 + 训练推高 logit，
  两者碰到一起才出事，单独存在都不会崩。

## L5.11 评测前先确认测的是你的模型（E002 实录）

### 问题

`mlx_lm.server` 按请求体里的 `model` 字段路由模型：只有 `model == "default_model"`
时才使用启动参数 `--adapter-path` 挂的 adapter；写具体模型名（如
`mlx-community/Qwen2.5-7B-Instruct-4bit`）会被当成"换模型"，服务按这个名字
重新加载一个**不带 adapter 的基座**。我们的客户端曾长期发基座模型名
（历史上为修一个 404 把 `"default"` 改成了基座名——报错消失了，
但请求从此落到基座上），导致此前全部评测测的都是基座。

### 识别"测错模型"的反常信号

- loss 持续下降，但评测行为毫无变化；
- 两个训练量差很多的 checkpoint，temperature=0 下输出大量逐字相同
  （42/60——其实是同一个基座被测了两次）；
- 输出风格不像训练数据：训练集每条引用都带〔〕和 `（YYYY-MM-DD）` 版本标签，
  60 题一次都没出现。

### A/B 冒烟法（每次评测前做）

同一个服务进程、同一道题、同一 system prompt、temperature=0，
只改请求的 `model` 字段各发一次：`default_model`（应含训练格式标记）
vs 基座模型名（应是基座风格）。两次输出明显不同 = adapter 确实挂上了；
逐字相同 = 没挂上，先排查再评测。脚本 `scripts/experiments/e002/ab.py`。

### 可追溯性

- `tu serve model` 写的 `current.json` 记 `model=default_model` + `base_model` + `exp`；
- 评测 manifest 的 config 记 `model`/`exp`/`base_model`，事后能还原"测的是哪个 adapter"；
- `runtime.model_name` 显式配置成具体模型名时仍按配置走，这是调试基座的逃生门。

## L5.12 如何区分曝光不足、记忆不足与泛化不足（E003）

看见低召回不等于证明模型的参数容量到顶。先把一个预测拆成三级：
找对文件、找对条、找对款；然后检查目标条款在训练集中出现了几次。
E002 的 7B 模型已从基座的 1/60 条级命中提升到 17/60，但 gold 条款
曝光中位仅 2 次，不能从 0.150 的严格款级召回直接跳到"必须换架构"。

一个低成本实验是取训练原题、排除问句直接点名条款的题，和新问法的
人工评测集对比。如果原题能答、新问法不能，优先查问法泛化；
如果原题也不行，再增加曝光试验，比较**同一模型追加训练前后**
两套题的变化。训练原题并非独立测试集，不可用它宣称真实场景准确率。

E003 的原题探针（P1）条级 15/52 (0.288)，人工评测集为 17/60 (0.283)，
暂不支持"只差泛化"。数据顺序复核还发现续训漏掉尾部约 500 条；
它们的 loss 为 0.565，随机已训 500 条为 0.475，可作为同分布的问法对照
（P3，条级 50/223）。这些组的条款和难度不完全相同，不宜用非配对
显著性检验当因果证明。

**追加一个 epoch 的结果**：仍用相同数据、从训满版 adapter 续训，改用
seed 43 重新打乱。探针 P2 的条级命中由 28/100 升至 51/100，
P3 由 50/223 升至 132/223（P3 的原题第二轮才首次出现）；
但独立人工评测 v1 仅由 17/60 升至 18/60，严格款级仍是 9/60。
同一批题目的配对检验显示 P2/P3 的提升显著，v1 未测到显著提升。
这说明**增加曝光确实能提高训练分布上的定位，不能说训练没有教进知识**；
但也不能把训练原题的提升当作自然咨询能力已经提升。v1 样本只有 60 条，
“未测出改善”不等于证明效果绝对为零。下一步应优先考虑同条款多问法
与检索补全，不要未经检验就把瓶颈归为 LoRA 参数容量；
实际执行过程见 `docs/experiments/E003-run-log.md`。

## L5.13 换更大的模型、更多数据、更好的硬件，能解决什么

POC 的训练目标只是证明"模型从训练中学到了知识，能答对一部分问题"，
E002/E003 已经证明（与基座比，条级 1/60 → 17/60）。正式阶段如果换更大的底座、
用更多数据和更好的 GPU，各因素的作用不同：

| 因素 | 能改善什么 | 解决不了什么 |
|---|---|---|
| 更大的模型 | 预训练法律知识更多；对新问法更能联想到对应条款 | 训练数据只有一两种问法时，泛化问题只是缓解 |
| 更多同类数据（重复曝光） | 训练分布内的题目记得更牢（E003：P2 28→51/100） | 换个问法仍答不出（E003：v1 17→18/60） |
| 更多样的数据（同一条款多种问法） | 直接针对"换个问法就答不出" | 条款极多、措辞相近时的精确定位仍难 |
| 更好的硬件 | 可用高精度、更高 rank 或全参数微调，不再需要 fp16 补丁 | 本身不提升泛化，只是放开限制 |

研究上的对应结论：模型能否在新问法下提取知识，关键在于训练数据中同一知识
有没有多种表述（Allen-Zhu、Li，*Physics of Language Models* Part 3 系列）；
单靠微调注入新知识，效果一般不如检索（Ovadia 等，2023）。

所以排序是：**数据多样化 > 模型规模 > 训练配置**。"越大越好"在本项目中还没有做过
干净的对照实验，正式立项前应先用小规模实验验证。完整判断见
`docs/experiments/poc-training-summary.md` 第 4 节。

## L5.14 文件、条、款三级命中，以及 SC-016 为什么按文件选题

同一个"引用对不对"要拆成三层看，严格程度递增：

| 级别 | 判定（宽松解析输出里的 `《文件名》第N条`） | 例：gold 是 `a24:p2` |
|---|---|---|
| 文件 | 输出的 `《文件名》` 能匹配到知识库里同一文件 | 写对法名、没写条号也算对 |
| 条 | 文件对 **且** 写出了正确的条号（带款、项也算） | `《劳动合同法》第二十四条` |
| 款 | 校验层解析、规范化出的完整条款 ID 与 gold 完全一致 | `第二十四条第2款` 或"第二款"被解析成 `a24:p2` 都算；原文小有出入被校验层纠正后对上 `a24:p2`，同样计为命中 |

注意款级看的是**校验之后**的 `cited_clause_ids`，不是输出原文的逐字比对：
校验层会把"第二款"这类写法规范化，也会纠正引用文本，只要最终解析出的
完整 ID 与 gold 一致就计为严格命中。

基座模型也能"蒙"对文件（凭预训练记忆猜得到该查哪部法），所以单看文件级
会把"本来就有的能力"算成训练成果。SC-016 的第③条因此只统计
**基座在整个评测集上从未识别过的那些 gold 文件**对应的题目：
同一文件只要被基座答对过一题，该文件的所有题都退出子集——因为
无法排除基座"碰巧认识这个文件"。子集里基座 0/30、自训模型 21/30，
说明自训模型在基座未命中的文件子集上表现更好。反过来，如果基座把
全部文件都识别过，子集为空，第③条"无法判定"，整条 SC-016 不能算通过。

判定命令：`tu eval compare --sc016 <基座 run> <自训 run>`。
它只统计 `category=clause_id` 的用例，先核对两个 run 的知识库、
评测集、温度和 system prompt 设置一致，再逐项判定；三项都过返回
退出码 0，可作为 T075 续训后的回归门槛（回归阈值另按 T075 的
条级 ≥17/60、款级 ≥9/60 基线判断）。
