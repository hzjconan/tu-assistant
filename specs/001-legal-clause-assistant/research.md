# Research: 工会法律条款智能助手（POC）

**Feature**: `001-legal-clause-assistant` | **Date**: 2026-11-10 | **Plan**: [plan.md](./plan.md)

本文记录 plan 阶段的技术决策。每条决策格式为：决策 / 理由 / 考虑过的替代方案。

**当前阶段为 POC**：30–50 篇文档，尽量快、只用开发者本机（M1 Pro / 32GB），重点是跑通全流程并能演示。
模型效果优化、1000 篇规模验证、对照实验等留到正式阶段，集中记录在 [R12](#r12-留到正式阶段的事项)。

---

## R1. 技术路线：把知识训进模型参数 + 出处校验层

**决策**：选一个开源基座模型，通过指令微调（SFT）把知识库内容和对话行为一起训进模型参数，推理时**不做检索**。
模型输出后，由确定性的**出处校验层**按条款编号查条款库、逐字比对并纠正引用原文（R5）。

**理由**：
- 项目方明确选择该路线（本质需求：私有部署 + 模型本身学过项目方的文档）。
- 宪章原则 I 要求条款原文必须与知识库逐字一致；校验层按编号查表，不属于检索，与该路线兼容。
- 实际入库 25 篇文档的训练数据约 1.5–2.5M token，本机一晚可训完一轮（R10）。

**已知风险**（POC 中观察，正式阶段解决）：
- 精确复述条款编号与原文是该路线弱项；"编号真实存在但引错了条"无法被校验层拦截，只能靠评测发现。
- POC 结果不能外推到 1000 篇规模。

**替代方案**：检索 + 通用模型、检索 + 自训模型——作为正式阶段的对照组与回退选项（R12）；从零预训练——不可行。

## R2. 基座模型

**决策**：
- **演示用**：`Qwen/Qwen2.5-7B-Instruct`（Apache 2.0）。
- **调试流程用**：`Qwen/Qwen2.5-1.5B-Instruct`（Apache 2.0）。
- 本机使用 `mlx-community` 的 4bit 版本训练与推理。

**理由**：
- 必须允许商用 + 私有部署：两者均为 Apache 2.0。
- **排除 `Qwen2.5-3B`**：Qwen Research License，仅限非商业；本机测速用过，不得作为产品基座。
- 7B 在本机已实测速度与内存（R10），风险最低；多轮追问、多违法行为识别需要一定推理能力，1.5B 只用于调通流程。
- `Qwen3.5-9B` 更新更强，但词表约 24.8 万（Qwen2.5 为约 15 万），长样本训练时输出层内存压力更大，本机未实测；POC 不采用，留到正式阶段（R12）。

**替代方案**：Qwen3.5-4B（同代小尺寸，未实测）；DeepSeek / GLM 小尺寸模型（需逐个核实许可与工具链）。

## R3. 训练方案

**决策**：**一次 SFT**，把知识样本和行为样本混合训练。不单独做继续预训练（CPT），不做偏好优化（DPO）。

| 样本类型 | 说明 | 对应需求 |
|---|---|---|
| 条款复述 | "《X》第N条第M款的内容是什么" → 带出处的原文 | 记住原文与编号 |
| 编号与内容互查 | "关于X的规定在哪一条" ↔ "第N条讲什么" | 编号与内容双向可提取 |
| 改写问答 ×3–5 | 同一条款用不同问法、通俗解释、案例化描述提问和回答 | 换个问法也能答出 |
| 条款关系 | "违反第N条要承担什么责任" → 对应法律责任条款 | 关联补全（FR-019） |
| 多轮意图确认 | 模糊开场 → 追问（≤N 个问题，N 取 2–6 随机，写在 system prompt 中）→ 确认意图 → 回答 | FR-009 ~ FR-013 |
| 咨询回答 | 按引用格式（contracts/citation-format.md）输出条款 + 适用分析 + 法律责任 | FR-015 ~ FR-023 |
| 多违法行为 | 一段案情含多个行为、多个主体，逐一认定 | FR-016、FR-026 |
| 例外与边界 | 存在例外情形；信息不足时追问或分情形 | FR-018 |
| 拒答 | 知识库外的问题 → 明确拒答 | FR-022 |
| 普法文章 | 主题 → 多篇以案说法文章，虚构人物和单位，场景差异化 | FR-024 ~ FR-031 |
| 修改请求 | 对已生成文章的改写要求 | US2 场景 6 |
| 通用对话 | 少量通用指令数据（约 5%） | 防止退化 |

**训练方式**：MLX QLoRA（4bit + LoRA），作用于全部线性层；长样本（普法文章）开梯度检查点。
超参（LoRA rank、学习率、轮数、序列长度）记录在实验清单（data-model：ExperimentRun）。

**理由**：一条训练流程最简单（宪章原则 VI）；知识以问答形式训进参数，比只训原文更容易被提取出来。
两阶段（CPT + SFT）记得更牢，但 POC 不追求效果，留到正式阶段。

**替代方案**：CPT + SFT 两阶段（正式阶段再做）；只训原文（换个问法就答不出）。

## R4. 训练数据合成

**决策**：用外部大模型 API（OpenAI 兼容接口）从**知识库中的公开文档**合成训练数据与评测候选用例。
提供方通过配置指定，默认 **DeepSeek API**。30–50 篇约需 ¥20–50。

**理由**：比在本机部署大模型合成快得多、质量高；DeepSeek 主力模型（V4.1-Flash 约 552B）无法在本机部署，
本机能跑的小模型合成质量不够。

**合规约束**（宪章原则 III、IV）：
- 只允许把公开法律文档与公开案例发给外部服务；用户对话内容永远不进入合成流程。
- 外部服务只出现在离线的合成与评测打分模块中，运行时禁止调用（R7 的端点白名单）。
- 每批合成数据记录提供方、模型名、提示词版本、随机种子（宪章原则 VI）。
- 使用前确认提供方的服务条款允许用其输出训练模型。

**质量控制**：合成样本先过自动检查（引用格式可解析、引用的条款存在、原文一致），不通过的丢弃；再人工抽检。
评测用例与训练样本用不同的提示词生成，并按条款与问句相似度去重，保证评测问法与训练数据不同（宪章原则 V）。

**替代方案**：在 5090 上部署 27–35B 开源模型本地合成——零费用、数据不出域，但需先搭环境，留到正式阶段（R12）。

## R5. 出处校验层

**决策**：模型输出按约定的引用格式标注每一处条款引用（contracts/citation-format.md）。
校验层是确定性程序，对每处引用：

1. 解析出 文件名 + 版本 + 条 / 款 / 项编号；
2. 在条款库中按编号查找：
   - **找不到**（编号或文件不存在）→ 删除该引用块，标注"此处引用未通过校验"，记录为校验失败；
   - **找到但原文不一致** → 用条款库原文替换，记录为"已纠正"；
   - **找到且一致** → 保留；
3. 检测未按格式标注的裸引用（如正文里出现"第五十一条"但没有出处标记）→ 记录为"出处不完整"。

**评测口径**：条款引用准确率（SC-007）分别统计**校验前**（模型原始输出）和**校验后**（交付给用户的输出）。
校验后应恒为 100%；**校验前的准确率反映模型真实记住了多少**。

**理由**：宪章原则 I（比对不通过的内容不得交付）；也是演示时体现可信度的关键。按编号查表实现简单、可测试。

**替代方案**：限制解码（只允许生成存在的编号）——实现复杂，先不做。

## R6. 对话编排

**决策**：对话行为（意图确认、追问、改写）由模型本身完成（通过 SFT 学会）；编排层只做确定性的工作：

| 职责 | 实现 | 对应需求 |
|---|---|---|
| 会话上下文 | 内存中保存单次会话的消息，会话结束即释放，不落盘 | FR-009、FR-033 |
| 追问上限 | 从配置读取 `max_questions_per_turn`（默认 5）写入 system prompt；输出后统计问题数，超限记入指标 | FR-011 |
| 出处校验 | R5 | FR-006 ~ FR-008 |
| 关联补全兜底 | 输出引用的条款若有已确认（`confirmed`）的关联条款未被引用，按 ClauseRelation 在末尾追加"相关条款"提示（原文取自知识库），记录为补全 | FR-019 |
| 免责提示 | 咨询回答末尾固定追加 | FR-023 |
| 身份信息检查 | 见下 | FR-030 |
| Markdown 导出 | 把回答或文章保存为 `.md` 文件 | FR-032 |

**身份信息检查**：从本会话用户消息中用规则抽取候选身份信息（单位名称后缀如"公司/厂/集团/医院/学校"、常见姓氏 + 名字模式）。
普法文章生成后检查是否包含这些字符串，命中则替换为虚构名称并记录。

**理由**：能确定性完成的事交给程序，保证可测试；追问上限放在 system prompt 中，并在训练数据里让 N 随机变化，
模型才能学会遵守可配置的上限。

**替代方案**：规则状态机控制对话（僵硬，难以覆盖大白话开场）。

## R7. 推理服务与演示界面

**决策**：
- 模型用 `mlx_lm.server` 在本机提供 OpenAI 兼容接口。
- 编排层通过配置中的端点访问模型；**运行时端点必须在白名单内**（默认 `127.0.0.1`、`localhost`），
  不通过则拒绝启动（宪章原则 III、IV）。外部 API 客户端只存在于合成与评测模块中。
- 演示界面：本地网页对话界面（Gradio），支持多轮对话与保存 Markdown；另提供命令行对话工具便于调试。
  演示界面是 POC 的重点交付物之一。

**理由**：OpenAI 兼容接口让正式阶段换成 vLLM 时不改编排代码；Gradio 实现成本最低。
本机实测 7B 生成约 35 tok/s：咨询回答 10–20 秒，3 篇普法文章约 1 分钟，可满足演示。

**限制**：本机训练时无法同时演示，演示前需停止训练。

**替代方案**：自建前端 + 后端服务（POC 不需要）。

## R8. 文档入库与条款拆分

**决策**：
- 支持 `.docx`（python-docx）、文本型 `.pdf`（pdfplumber）、`.html`（BeautifulSoup）、`.txt`；统一转为纯文本后拆分。
- 拆分规则基于中国法律文本的结构标记：`第X编/章/节`、`第X条`（条）、条内自然段（款）、`（一）（二）`（项）。
  中文数字编号转为整数存储，同时保留原始写法。
- 条款关联：用规则抽取文内显式引用（"违反本法第X条""依照第X条"），再人工确认。50 篇规模人工核对得过来。
- 入库校验：编号连续性、重复、空条款；问题清单输出供人工核对（FR-005）。
- 文档更新：POC 阶段整批重新导入，不做增量更新。

**依赖项目方**：拆分规则需用真实文档验证；**请尽早提供 1–2 份样例文档**。

**替代方案**：用大模型做结构化抽取或关联分类（不可复现、难以校验；正式阶段可作为辅助）。

## R9. 评测

**决策**：POC 评测集约 **60–80 题**，版本化管理（data-model：EvalCase）。

| 类别 | 题数（约） | 打分方式 |
|---|---|---|
| 条款识别（单行为） | 15 | 自动：引用解析后与标准条款集合比对 |
| 多违法行为 / 多主体 | 10 | 自动 + 违法主体匹配 |
| 例外与边界 | 8 | 自动 + 人工看 |
| 范围外拒答 / 误拒 | 12 | 自动（拒答判定） |
| 意图确认（多轮） | 10 | **固定对话脚本**（预先写好用户每轮说什么），自动判定确认轮次与意图 |
| 普法文章 | 10 | 项目方按评分要点人工评审 |

- 指标：spec SC-001 ~ SC-011（SC-012 规模稳定性留到正式阶段）；POC 阶段阈值只作目标值。
- 评审意见：POC 用表格记录（FR-037）。
- 不使用用户模拟器和评判模型，评测不调用外部服务、不产生费用。

**理由**：宪章原则 V 要求有评测，但 POC 只需要能测出来、看得到差距；固定脚本和人工评审最省事，结果也可复现。

**替代方案**：≥200 题 + 用户模拟器 + 评判模型（正式阶段再做）。

## R10. 资源估算

**本机实测**（M1 Pro / 32GB，MLX LoRA rank 8，2026-11-10）：

| 模型 | 场景 | 训练速度 | 峰值内存 |
|---|---|---|---|
| Qwen2.5-7B-4bit | 短样本（≤750 token） | ~100 tok/s | ~9GB |
| Qwen2.5-7B-4bit | ~5k token 样本 | ~97 tok/s | 23GB |
| Qwen2.5-7B-4bit | ~5k token 样本 + 梯度检查点 | ~83 tok/s | 11.5GB |
| Qwen2.5-7B-4bit | 推理 | 生成 ~35 tok/s | 4.5GB |
| Qwen2.5-0.5B-4bit | 短样本 | ~1,150 tok/s | — |

结论：长样本必须开梯度检查点；1.5B 未实测，按 0.5B 与 7B 之间估计。

**数据量估算**（以每篇约 6 千 token 计，拿到真实文档后修正）：

| 项目 | 数量 |
|---|---|
| 原文 | ~0.3M token |
| 知识类样本（复述、互查、改写 ×3–5、条款关系） | ~1–2M token |
| 行为类样本（多轮、咨询、拒答、普法文章等，约 1.5k 条） | ~1–2M token |
| **合计** | **~2–4M token** |

**时间与费用**：
- 1.5B 调试：一轮数小时以内。
- 7B 演示模型：一轮约 6–12 小时（一晚），训 2 轮约一到一天半。
- 数据合成：外部 API 约 ¥20–50。
- 无硬件费用、无云 GPU 费用。

**本机环境**：模型下载使用 `HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1`（本网络下直连与 xet 极慢）；
Python 环境用 uv 管理并锁定依赖版本；新增依赖优先选择发布超过 7 天的版本。

## R11. 5090 工作站（可选）

**决策**：POC 默认不使用。只有当"每次改数据都要等一晚"成为瓶颈时，才接入项目方的 Linux + RTX 5090 工作站加速训练。

**接入方式**（届时）：ZeroTier 内网 SSH + SSH 密钥；训练在 `tmux` 中运行；代码走 git，产物用 `rsync` 同步 `artifacts/`。

**风险**：Blackwell 架构需要 CUDA 12.8+ 与较新的 PyTorch；bitsandbytes、flash-attention 支持可能滞后。
接入前需先做一次与本机相同的训练实测。

## R12. 留到正式阶段的事项

POC 之后进入正式阶段（约 1000 篇文档）时，按以下清单补齐：

| 事项 | POC 的处理 | 正式阶段要做的 |
|---|---|---|
| 规模验证 | 不做 | 50 / 200 / 500 / 1000 篇规模曲线，验证"知识训进参数"在 1000 篇下是否成立（spec SC-012、FR-036） |
| 对照组 | 不做 | 检索 + 同一基座（未微调）作为评测基准；BM25 + bge-m3 向量检索按条款召回，RRF 融合 |
| 决策关卡 | 不设 | 1000 篇规模下全部达标 → 继续；与对照组差距 ≤5 个百分点 → 补数据或 DPO 后复测；更差 → 由项目方决定是否改为"检索 + 自训模型" |
| 训练方案 | 一次 SFT | CPT（原文 + 改写 ×~10 + 条款关系 + 通用语料）+ SFT；按需 DPO |
| 基座 | Qwen2.5-7B | 评测 Qwen3.5-9B 等更新模型；核实工具链支持 |
| 训练硬件 | 本机 | 5090 bf16 LoRA；仅在需要全参数微调时申请云 GPU |
| 推理服务 | mlx_lm.server | vLLM |
| 评测集 | 60–80 题，固定脚本 + 人工 | ≥200 题，用户模拟器 + 评判模型 + 法律专业人员复评 |
| 数据合成 | 外部 API | 考虑在 5090 上部署 27–35B 开源模型本地合成，关键节点用外部 API 复核 |
| 条款关联 | 规则 + 人工 | 增加大模型辅助分类 |
| 知识库更新 | 整批重导 | 增量更新 |
| 评审意见 | 表格 | 系统内录入（FR-037） |
| 存储 | SQLite | 视部署需要评估是否换成 PostgreSQL（多人同时维护、并发评审时） |
