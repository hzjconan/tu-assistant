# Task Implementation & Independent Review Loop

每个 task 实施完成（或按外部模型评审意见返工完成）、向用户汇报验收前，必须执行本闭环（最多 5 轮）。本规范不绑定特定 CLI 或模型，与 `.agents/skills/task-handoff/SKILL.md` 上下游衔接，支持自动降级。

## 适用边界与红线

- **绝对红线**：无论实施方还是复审方，**严禁读取 `inputs/` 目录下的任何文件**（包括直接读取、grep 或运行输出其内容的脚本；除非用户明确书面授权读取范围）。
- **不得提前收口**：在向用户汇报并得到明确确认（通常用户会再交由外部模型复审）之前，**不得勾选 `specs/*/tasks.md` 中的对应任务，不得 `git commit`，不得 `git push`**。
- **审查员零副作用**：审查员只允许只读读取、只读查询与无副作用检查（如 `pytest` / `ruff` / 只读 `python -c` 探测），**严禁修改任何文件，严禁运行会向 `artifacts/` 或仓库写入产物的命令**（如 `tu kb import`、`tu eval run` 等）。
- **意见分级**：
  - **阻断项**：功能/逻辑 bug、违背定稿执行单或宪章原则、执行单自身遗漏或假设有误导致的真实缺陷、跨模块漏接或只读保护破坏、测试假阳性或缺失关键反例、数据/实测口径失真或不可追溯、运行时隔离被破坏。
  - **非阻断建议**：风格微调、可读性改进、改动面较大可延后到下游任务的优化。

## 闭环步骤（最多 5 轮）

### 第 1 步：完成实现与送审前自检

1. 严格按已拍板定稿的 `docs/handoffs/<task>-handoff.md`（遵循其中的改动范围、不做清单、接口契约、测试矩阵与偏差止损规则）完成代码、测试、产物及 `docs/learning/` 学习文档更新。
2. 跑通对应单测、全量 `uv run --offline --no-sync pytest`、`uv run --offline --no-sync ruff check src tests`（覆盖改动到的脚本）及只读基线校验（如 `shasum -a 256 -c artifacts/logs/t075/01/output.sha256`）。
3. 核查 `git status` / `git diff`，确认无意外改动、无遗留临时/沙箱空目录、历史只读产物未动且 `tasks.md` 对应项仍未勾选。
4. **留存送审前快照指纹**：在派发审查员前记录 `git status --porcelain` 与 `git diff | shasum`（用于在审查员返回后核验字节级零修改）。

### 第 2 步：派发独立只读复审（Round 1）

启动一个**隔离上下文的独立审查员**（看不到主会话的实现过程和推理历史），按以下三级优先级选择机制（工具无关，自动降级）：

1. **首选 · 单节点高思考审查员（适用于支持按具体模型/思考等级拉起单节点的工具，如 Antigravity 的 `swarm`）**：
   - **仅拉起 1 个审查节点**（如首轮 `name="reviewer"`、外部评审返工轮 `name="reviewer-v2"`，`workspace="inherit"` 不建 worktree，严禁并发拉起多个节点）；
   - 精确指定高思考模型（如 `gemini-4-neon-high`，若不可用则选同系列最高可用思考档位），实现“实施用便宜档省额度、审查用高思考保质量”；
   - 若审查节点默认具备写工具，必须在 `brief` 中明文约束只读零修改与禁写副作用命令；**每轮复审返回后比对送审前 `git status --porcelain` 与 `git diff | shasum` 确认字节级零修改**；
   - 闭环结束后立刻回收（`kill`）该审查节点。
2. **降级 1 · 独立只读子代理（适用于无单节点精确模型能力但支持子代理的 CLI，如只读 `research` 子代理 / 其他 CLI 的 Agent/Task 工具）**：
   - 派发隔离上下文的只读子代理；若接口支持模型档位或思考等级参数，优先选高档位（如 `pro` / `high`），否则继承主会话配置。
3. **降级 2 · 无子代理能力兜底**：
   - 若当前 CLI 完全不支持派发子代理，须在最终汇报中明确注明“当前工具无子代理能力，跳过内部复审”，按下方必查清单完成逐项自查并附上完整证据与改动清单，直接交用户转外部模型复审。

**发给审查员的 `brief` 必须明文包含以下 4 项**（新节点看不到主会话上下文，不得省略）：
1. **先完整阅读 `.agents/skills/task-review-loop/SKILL.md`**，按本规范的零信任原则、双重审查视角与 6 类攻击面必查清单执行；
2. **只读红线**：禁止修改任何文件、禁止运行向仓库或 `artifacts/` 写文件的命令、严禁读取 `inputs/`；
3. **审查目标与范围**：目标执行单路径 `docs/handoffs/<task>-handoff.md`、本轮改动说明（如属外部评审返工，一并附上外部评审意见原文）；
4. **统一输出格式**：**结论（通过 / 需修改）→ 阻断项（带 `file:line` 与复现/反证依据）→ 非阻断建议 → 逐项核查证据**。

#### 审查员核心审查纪律（零信任 + 双重审查 + 6 类必查攻击面）

- **零信任独立复验**：不得轻信实施方在 `brief` 中的口头汇总；必须自己运行只读 `git status` / `git diff` 确认**真实全量改动面**，直接读取改动源码与测试全文，并按需独立复跑关键只读测试/校验命令。
- **双重审查视角**：
  1. **对照执行单查落地**：是否完整落实定稿执行单的改动表、不做清单、接口契约、测试矩阵与文档更新点；
  2. **跳出执行单找真实工程缺陷**：不得盲信执行单中的所有假设；主动核查跨模块调用方、第三方库真实源码/运行时行为与端到端业务路径——**即使执行单本身写漏或假设有误，只要构成真实 bug 或风险，同样判为阻断项**。
- **6 类高频攻击面必查清单（逐项过筛）**：
  1. **跨模块接线与复用一致性**：是否新建了工厂/辅助函数却未接入生产调用方？同类入口（如 `cli.py`、`eval/`、`chat/`、`ui/`）是否漏改或重复造轮子？
  2. **第三方库与并发/生命周期陷阱**：必要时只读核查第三方库源码或实测行为（线程安全、asyncio 事件循环阻塞、缓存/临时文件与 SQLite 连接回收、多余暴露面如 `allowed_paths`）；
  3. **异常路径与边界输入**：空输入、`None`/`null`、`nan`/`inf`、坏文件、外部服务断连或链路中途抛错时，状态（如会话消息、`intent`、连接）是否完整回滚清理？是否杜绝静默建空库或静默吞异常？
  4. **测试真实性与断言强度**：有无假阳性/弱断言（如仅断言 `returncode == 0`、`is not None`、warning 过滤过窄、漏断言透传参数、过度 mock 掩盖真实逻辑、未固定时间戳导致非确定性）？正反例与既有兼容回归是否齐备？
  5. **实测数字与文档口径真实性**：测试数、耗时/时间戳、统计数是否与实测日志逐字一致？实机联调到底是真实操作还是脚本/API 模拟，表述有无夸大？代码变更后受影响的联调/产物是否基于**最终代码**重跑？执行单与学习文档有无残留旧表述？
  6. **只读保护与仓库干净度**：`artifacts/` 历史只读产物与哈希锁是否完好？有无残留空目录/临时文件？`specs/*/tasks.md` 对应任务是否仍为未勾选 `[ ]`？

### 第 3 步：核实意见、严格修复或举证异议

收到复审报告后，先比对送审前快照指纹确认审查员零修改，再逐条核实：
- **认同的阻断项**：必须根因修复，并补齐针对该阻断项的确定性回归测试。
  - **实施方修复纪律**：严禁通过静默 `except` 吞错、删测试、放宽断言来“消除”阻断项；若发现阻断项涉及修改既定接口签名、改写既有测试预期或扩大改动范围，须按执行单的“偏差止损规则”审慎评估或先上报用户。
- **认同的非阻断建议**：仅在**改动小、低回归风险**时顺带修复；涉及较大重构或范围膨胀的，记入下游任务备忘而非强行塞进本轮。
- **有异议的条目**：不得直接忽略；必须整理具体 `file:line`、规范条款或实测命令输出，说明为何不改。
- **同步与全量回归**：每次修复后，必须同步清理执行单/学习文档中的关联旧表述，并重跑全量 `pytest`、`ruff` 与只读基线校验（若改动影响了已做过的实机联调或产物，须基于最新代码重跑），**严禁拿未过全量门禁的半成品唤醒下一轮复审**。

若本轮**阻断项 = 0 且无待审核的修复或未决异议**，闭环顺利结束（先回收审查节点），跳至第 5 步。

### 第 4 步：提交下一轮复审（Round 2 … 5）

- 再次留存送审前快照指纹（`git status --porcelain` + `git diff | shasum`）；
- **优先复用同一审查员会话**（单节点 `swarm` 在公告板 `@reviewer` 续聊；子代理向原会话继续发消息），节省重复上下文并保持审稿口径连贯；
- 若当前 CLI 不支持向同一审查会话继续对话，则新开只读审查会话并完整附上：上一轮问题清单、本轮 `git diff`（或改动摘要与文件行号）、最新全量验证输出、以及异议与证据；
- **Round 2+ 审查聚焦与防漂移**：要求审查员重点复核 ① 上轮阻断项是否真正根治且有回归测试；② 异议证据是否成立；③ 本轮修复是否引入新回归（含文档同步）；不得对未改动代码反复冒出新的低优先级风格意见卡通过（但发现遗漏的真实严重缺陷仍应阻断）；
- 回到第 3 步，重复循环。

### 终止条件

满足以下任一条件即停止循环（停止前务必回收审查节点并比对快照指纹确认审查员零修改）：
1. **一致通过**：审查方判定阻断项 = 0，且双方无未决异议；
2. **僵局早停（防便宜模型空转）**：同一阻断项连续 **2 轮**修复仍未实质收敛，或触发执行单偏差止损红线——提前中止，整理根因、两轮尝试与卡点交由用户决策（或由用户改派高思考模型收尾）；
3. **达到上限**：已完成 **5 轮**独立复审仍未达成一致（强制停止，不得继续空转）。

### 外部模型复审返工条款

当用户将本轮成果交给外部模型复审并带回修订意见要求返工时，落地修改（及必要的代码变更后重跑实机联调/产物）后，**同样必须执行本闭环**（新拉 1 个独立审查节点如 `reviewer-v2`），重点核查：外部评审条目是否全部落地（含执行单/学习文档旧表述清理）、修复是否引入新回归、以及受影响的验收/联调是否基于最终代码重跑。

### 第 5 步：落盘记录、终检与向用户汇报

无论一致通过、僵局早停还是满 5 轮停下：
1. 将完整复审结果写入该任务的执行单（`docs/handoffs/<task>-handoff.md`）；
2. **汇报前 3 项一致性终检（防止收尾写文档引入低级失误）**：
   - 运行 `git diff --stat` 与 `git status`，核对与待审改动文件清单完全一致；
   - 核实 `specs/*/tasks.md` 对应任务仍为未勾选 `[ ]`；
   - 逐项核对即将汇报的测试数、哈希校验、联调方式（实操 vs 模拟）与最后一次实测命令输出逐字一致。
3. 在对话中向用户精简汇报：
   - **闭环结果**：共进行几轮复审、结束原因（一致通过 / 僵局早停 / 达到 5 轮上限）；
   - **每轮问题与处置**：阻断项如何修复、非阻断建议采纳或留档情况；
   - **未决分歧或僵局卡点（如有）**：并列呈现审查方观点、实施方证据/尝试，交由用户及外部模型裁决；
   - **验收证据**：`pytest`、`ruff`、只读哈希校验、联调/产物校验等实测命令与精确结果；
   - **待审改动文件清单**：方便用户直接交给外部模型复审；明确标注对应任务**尚未勾选、尚未 commit**。
