# Task Implementation & Independent Review Loop

每个 task 实施完成、向用户汇报验收前，必须执行本闭环（最多 5 轮）。本规范不绑定特定 CLI 或模型，适用于任何具备或部分具备子代理能力的实施方。

## 适用边界与禁止事项

- **绝对红线**：无论实施方还是复审方，都不得读取 `inputs/` 目录下的任何文件（除非用户明确书面授权读取范围）。
- **不得提前收口**：在向用户汇报并得到明确确认（通常用户会再交由另一模型复审）之前，**不得勾选 `specs/*/tasks.md` 中的对应任务，不得 `git commit`，不得 `git push`**。
- **意见分级**：
  - **阻断项**：功能/逻辑 bug、违背执行单或宪章原则、测试假阳性或缺失关键反例、数据/产物不可追溯或口径矛盾、运行时隔离被破坏。
  - **非阻断建议**：风格微调、可读性改进、可延后到下游任务的优化。

## 闭环步骤（最多 5 轮）

### 第 1 步：完成实现与自检
1. 按已获批的 `docs/handoffs/<task>-handoff.md` 完成代码、测试、产物及 `docs/learning/` 学习文档更新。
2. 跑通对应单测、全量 `uv run pytest` 和 `uv run ruff check`（覆盖改动到的脚本与源码）。
3. 核查 `git status` / `git diff`，确认无意外改动或历史只读产物被修改。

### 第 2 步：派发独立只读复审（Round 1）
启动一个**隔离上下文的独立审查员**（看不到主会话的实现过程和推理历史），按以下三级优先级选择机制（工具无关，自动降级）：

1. **首选 · 单节点高思考审查员（适用于支持按具体模型/思考等级拉起单节点的工具，如 Antigravity 的 `swarm`）**：
   - **仅拉起 1 个审查节点**（如 `name="reviewer"`，`workspace="inherit"` 不建 worktree，严禁并发拉起多个节点）；
   - 精确指定高思考模型（如 `gemini-4-neon-high`，若不可用则选同系列最高可用思考档位），实现“实施用中档省额度、审查用高档保质量”；
   - 若审查节点默认具备写工具，必须在任务说明（`brief`）中明文约束：**只读核查，严禁修改任何文件、严禁读取 `inputs/`**；每轮复审后用 `git status` 确认其零修改；
   - 闭环结束后立刻回收（`kill`）该审查节点。
2. **降级 1 · 独立只读子代理（适用于无单节点精确模型能力但支持子代理的 CLI，如只读 `research` 子代理 / 其他 CLI 的 Agent/Task 工具）**：
   - 派发隔离上下文的只读子代理；若接口支持模型档位或思考等级参数，优先选高档位（如 `pro` / `high`），否则继承主会话配置。
3. **降级 2 · 无子代理能力兜底**：
   - 若当前 CLI 完全不支持派发子代理，须在最终汇报中明确注明“当前工具无子代理能力，跳过内部复审”，按相同核查项完成逐项自查并附上完整证据与改动清单，直接交用户转外部模型复审。

无论走优先级 1 还是 2，发给审查员的清单必须包含：
1. 只读核查，禁止修改任何文件，严禁读取 `inputs/`；
2. 对照 `docs/handoffs/<task>-handoff.md` 的范围与验收项逐项核查：
   - 源码实现、边界条件、与现有模块口径的一致性、运行时隔离；
   - 单元测试是否覆盖承诺的正反例、有无弱断言/假阳性；
   - 本轮产物/数据统计、可追溯字段及清单是否与实测逐项对账；
   - 执行单、学习文档、`tasks.md`（确认对应任务尚未勾选）口径是否一致；
3. 按统一格式返回：**结论（通过 / 需修改）→ 阻断项 → 非阻断建议 → 逐项核查证据**。

### 第 3 步：核实意见、修复或提异议
收到复审报告后，实施方逐条核实：
- **认同的阻断项**：必须修复，补齐回归测试并重跑验证。
- **认同的非阻断建议**：视性价比一并修复，或明确记入下游任务备忘。
- **有异议的条目**：不得直接忽略；必须整理具体代码行、规范条款或实测证据说明为何不改。

若本轮**阻断项 = 0 且无待审核的修复或未决异议**，闭环顺利结束（若使用了单节点 `swarm` 审查员，先回收节点），跳至第 5 步。

### 第 4 步：提交下一轮复审（Round 2 … 5）
- **优先复用同一审查员会话**（单节点 `swarm` 在公告板 `@reviewer` 续聊；子代理向原会话继续发消息），节省重复输入 token 并避免换人无限冒出风格意见；
- 若当前 CLI 不支持向同一审查会话继续对话，则新开只读审查会话并完整附上：上一轮问题清单、本轮改动 diff（或改动摘要及文件行号）、测试/验证输出、以及异议与证据；
- 要求审核员只重点复核：① 上轮问题是否真正修复；② 异议是否成立；③ 修复本身是否引入新回归；
- 回到第 3 步，重复循环。

### 终止条件
满足以下任一条件即停止循环（若使用了单节点 `swarm` 审查员，停止前务必回收节点并用 `git status` 确认审查员未改动任何文件）：
1. **一致通过**：审核方判定无未解决阻断项，且实施方与审核方无未决异议；
2. **达到上限**：已完成 **5 轮**独立复审仍未达成一致（强制停止，不得继续空转）。

### 第 5 步：向用户汇报（供外部模型复审）
无论顺利通过还是满 5 轮停下，将完整复审结果写入该任务的执行单（`docs/handoffs/<task>-handoff.md`），并在对话中向用户精简汇报：
1. **闭环结果**：共进行几轮复审、结束原因（一致通过 / 达到 5 轮上限）；
2. **每轮问题与处置**：阻断项如何修复、非阻断建议采纳或留档情况；
3. **未决分歧（如有）**：并列呈现审核方观点与实施方反驳证据，交由用户及外部模型裁决；
4. **验收证据**：`pytest`、`ruff`、产物校验等实测命令与结果；
5. **待审改动文件清单**：方便用户直接交给外部模型复审；明确标注对应任务**尚未勾选、尚未 commit**。
